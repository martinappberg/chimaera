# Claude Code: bidirectional stream-json

The current contract of the Claude Code driver (`src/claude.rs`). The pin is `TESTED_CLAUDE_VERSION`; the live gate is `just chat-smoke`. Each fact names the pass and the CLI version where it was recorded, for example "(Pass 31, claude 2.1.281)". "vsix" means mined from the official VS Code extension bundle (Anthropic.claude-code 2.1.204). "Original probe" means the first live probe (claude 2.1.206). A fact keeps the version it was seen at until a pass re-verifies it. The dated record is [passes.md](passes.md); the shared rules are in [cross-agent.md](cross-agent.md); the Mods surface is in [mods.md](mods.md).

## Spawn surface

The official extension's embedded SDK builds argv from `--output-format stream-json --verbose --input-format stream-json` plus the flags below (vsix, original probe).

| Flag | Notes | Chimaera |
|---|---|---|
| `--permission-prompt-tool stdio` | routes permissions to `can_use_tool` control requests | yes |
| `--include-partial-messages` | token-level `stream_event` deltas | yes |
| `--session-id <uuid>` | pins the native session id at spawn; `system/init` echoes it | yes |
| `--resume <id>` / `--continue` / `--fork-session` / `--resume-session-at` | session continuity | `--resume` yes; the fork flags are the rewind and branch path |
| `--settings <file>` / `--mcp-config <file>` | the same files the TUI spawns use | yes |
| `--model` / `--fallback-model <m>` | fallback when the primary is overloaded | model yes, fallback no |
| `--thinking adaptive` or `--thinking` + budget | thinking toggle at spawn | no; mid-session `set_max_thinking_tokens` instead |
| `--include-hook-events` | hook events on the stream | no; hooks arrive over HTTP |
| `--add-dir <dir>` | extra working directories | no |
| `--dangerously-skip-permissions` | required before `set_permission_mode bypassPermissions` is accepted | no; the normalized mode catalog does not offer bypass |
| `--no-session-persistence`, `--session-mirror` | | no |
| `--replay-user-messages` | echoes our own sends as `user` frames with `isReplay:true` (Pass 30, claude 2.1.259) | no |
| `--append-system-prompt-file` | a portable branch's bounded transcript, from a mode-0600 runtime file (Pass 24) | yes, for portable branches |
| `--advisor <model>` | the advisor server tool (Pass 33, claude 2.1.283) | no |
| `--forward-subagent-text` | opt-in subagent text and thinking in stream-json (Pass 15, claude 2.1.211) | no |

- Never pin `--session-id` together with `--resume` (original probe).
- `--help` at 2.1.310 versus 2.1.300 (help text only; no flag added or removed): `--resume` takes a session ID or a session name, `--disable-slash-commands` disables commands as well as skills, `--json-schema` works only with `--print`, and `--tools "default"` means the default set (Pass 52). The driver always resumes by id.
- `--model` accepts every catalog `value`, brackets included (`opus[1m]`); the server's argv charset guard admits `[` and `]`. `--model default` and any id spawn; the CLI validates the model at the first request (Pass 30, claude 2.1.259).
- `--permission-mode manual` is listed in the help; the control maps it to `default` (`{mode:"default"}` comes back) (Pass 30, claude 2.1.259).
- Environment: `DISABLE_AUTOUPDATER=1` pins the verified binary (original probe). `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true` turns on file checkpoints under `-p` (Pass 4). The daemon sets `CLAUDE_CODE_EMIT_TOOL_USE_SUMMARIES` for chat spawns unless `chat.toolSummaries` is off; the default is on (Pass 31).
- The MCP key rides in the URL inside the mode-0600 `--mcp-config` file (Pass 19 addendum).
- A host that sets `CLAUDE_CODE_DISABLE_CRON` (Claude Code's own desktop host does, for its children) disables loops in every child CLI. Probes and `just chat-smoke` scrub every `CLAUDE*` variable (Pass 47, claude 2.1.300).
- Never attach two live processes to one native session id: the transcripts interleave. The view toggle serializes on the chimaera session id (original probe).

## Handshake and initialize

- `system/init` is not emitted at spawn. The spawn handshake is a client-initiated `initialize` control request; the CLI answers at once (original probe).
- The `initialize` request declares `supportedDialogKinds: ["refusal_fallback_prompt", "fable_overage_consent_prompt"]`. A declared kind must be answered or it parks (Pass 7, vsix).
- The `initialize` response keys (Pass 43, claude 2.1.300): `account`, `agents`, `analytics_disabled`, `available_output_styles`, `capabilities`, `commands`, `current_permission_mode`, `fast_mode_disabled_reason`, `fast_mode_state`, `feedback_mode`, `ide_rc_auto_enable_gate`, `models`, `output_style`, `pid`, `remote_control_auto_connect_default`, `remote_control_auto_enable`, `remote_control_auto_on_by_default`, `remote_control_available`, `session_state` (`"idle"`), `user_output_styles_dir`, and `claude_code_version` ("2.1.300"). `hooks_applied`, seen at 2.1.259 (Pass 30), is gone. The key set and the 80-entry `commands` catalog are unchanged at 2.1.310 (Pass 52).
- The `initialize` response's own `capabilities` is `["ui_surface_v1"]` at 2.1.300; 2.1.310 adds `mcp_call_result_not_for_model_v1` (Pass 52). The driver keys behavior on the `system/init` list, never this one.
- `claude_code_version` is new in 2.1.300. The mapper journals it on `Init` only when the launcher's `--version` probe failed (Pass 43). See [cross-agent.md#version-detection](cross-agent.md#version-detection).
- `commands` is the slash-command catalog (names and descriptions; 61 entries at 2.1.259). The composer popover offers it. A command absent from it is unavailable in this mode (the CLI answers "/x isn't available in this environment") and gets native-UI interception (original probe). At 2.1.259 the catalog includes `/model`, `/effort`, `/mcp`, `/usage`, `/context`, `/fast`, `/compact`, `/rename`, `/recap`, `/goal`, `/loop`, `/batch`, `/schedule`, `/agents`, `/ultrareview`, `/code-review` and `/advisor`; the composer's native interception still wins for the ones chimaera renders itself (Pass 30, claude 2.1.259).
- `models` is the account model catalog: `[{value, displayName, description, resolvedModel, supportedEffortLevels (low|medium|high|xhigh|max), supportsEffort, supportsAutoMode, supportsFastMode, supportsAdaptiveThinking}]` (Pass 5). `supportsThinkingOff` (`@internal`) is new in 2.1.300, and `haiku` lists `supportedEffortLevels` low…max there, where 2.1.289 listed none; the catalog drives the effort control (Pass 43, claude 2.1.300).
- `current_permission_mode` seeds the mode chip at the handshake (Pass 30, claude 2.1.259).
- `fast_mode_state` (`off|cooldown|on`) and `fast_mode_disabled_reason` (`sdk_opt_in_required` on the probed account): fast mode needs an SDK-side opt-in whose control is unmined. Not adopted (Pass 30, claude 2.1.259).
- `remote_control_available` ("can be offered at all in this deployment… absent (older CLI) → treat as available") and `remote_control_auto_enable` ride `Init` as the two offer flags (Pass 30, claude 2.1.259). See [Remote Control](#remote-control).
- Parked-prompt redelivery: the response can carry `pending_permission_requests` and `pending_user_dialog_requests` (full request envelopes). The mapper replays them at the handshake, so a reattached client shows the cards (Pass 7, vsix).
- Startup hooks: `system/hook_started {hook_id, hook_name, hook_event}` and `system/hook_response {hook_id, outcome}` arrive before the `initialize` response. Concurrent SessionStart hooks can block the handshake; a `SessionStart:startup` hook that opened cloud-only files was cancelled at its configured 15-second timeout (`outcome: "cancelled"`), and the same workspace then initialized in 4.6 s (2026-10-01, claude 2.1.287). Chimaera must not silently disable user hooks to shorten startup. The driver journals bounded pending hook ids as `startup_progress` (never hook stdout or context). The shared harness allows 60 s; see [cross-agent.md#startup-lifecycle](cross-agent.md#startup-lifecycle).
- `system/init` is re-sent at every turn start (Pass 38, claude 2.1.283), after a background task settles and after a refusal fallback (Pass 30, claude 2.1.259). Every consumer resets on `Init`, so `Init` carries snapshots of state that outlives a turn (the Remote Control record).
- `system/init` fields (Pass 30, claude 2.1.259): `capabilities`, `skills`, `plugins`, `terminal_slash_commands`, `messaging_socket_path`, `memory_paths`, `product_feedback_disabled`, `fast_mode_*`, and (2.1.219+) `mcp_server_errors [{name, type, message}]`, the `--mcp-config` entries it skipped as invalid. `mcp_server_errors` becomes one Notice. `system/init` carries no task state (Pass 22, claude 2.1.212) and no advisor model (Pass 33).
- `capabilities` at 2.1.289 (2026-10-05): `interrupt_receipt_v1`, `interrupt_cancel_queued_v1`, `interrupt_send_now_v1`, `msg_lifecycle_v1`, `sdk_mcp_tools_list_changed`, `sdk_mcp_manifests`, `mcp_read_resource_v1`, `mcp_tool_ui_meta_v1`, `ui_surface_v1`. 2.1.300 adds `request_marker_lists_v1`; 2.1.310 adds `interrupt_requeue_taken_v1`, `lifecycle_wakeup_source_v1` and `mcp_call_result_not_for_model_v1`, 13 in all (Pass 52). The driver keys behavior on `msg_lifecycle_v1`, `interrupt_send_now_v1`, `interrupt_requeue_taken_v1` and `lifecycle_wakeup_source_v1` in the latest init (Pass 53).
- 2.1.310 `system/init` also carries `original_cwd` (the folder file-permission checks are anchored at; unlike `cwd` it does not follow the shell), `additional_directories` (every `--add-dir` / granted folder, absolute; `[]` when none) and `user_message_uuids`, all `@internal`. Not consumed (Pass 52).
- `system/init`'s `model` reports the resolved id, so current-model matching checks both `value` and `resolvedModel` (Pass 5).
- `--resume` keeps the resumed session id; the id comes from `system/init`, which is where the driver takes it (Pass 33, claude 2.1.283). Older CLIs forked a new id on resume.

## Control protocol

- `control_response` must nest `request_id` inside `response`. A top-level id is ignored and the CLI hangs (original probe).
- Client→CLI subtypes chimaera sends: `initialize`, `interrupt`, `set_permission_mode`, `set_model`, `set_max_thinking_tokens`, `get_settings`, `apply_flag_settings`, `get_context_usage`, `get_usage`, `generate_session_title`, `rewind_files`, `mcp_status`, `mcp_toggle`, `mcp_reconnect`, `stop_task`, `background_tasks`, `cancel_async_message`, `remote_control`. The shapes are in the sections below.
- CLI→client requests chimaera answers: `can_use_tool` (carries `tool_use_id`, `permission_suggestions`, `blocked_path`), `request_user_dialog`, `elicitation`. `control_cancel_request` withdraws one (original probe; Pass 7; MCP elicitation 2026-10-03).
- Other CLI→client subtypes seen: `hook_callback`, `mcp_message`, `oauth_token_refresh`, `host_auth_token_refresh` (Pass 7, vsix), and `remote_control_work_secret {session_id}` (only after an enable that passed `work_secret`, which chimaera never sends; Pass 30). Chimaera leaves an unknown subtype unanswered on purpose: the CLI parks it until its own deadline or another attached client settles it, and an error reply could break flows that rely on that fallback. A once-per-subtype Notice names what is waiting; the subtype name is capped by `UNHANDLED_REQUEST_NAME_MAX` and the remembered set by `UNHANDLED_REQUESTS_CAP` (2026-07-10; Pass 34).
- `{type:"keep_alive"}` frames are tolerated (Pass 7, vsix).
- Subtypes the extension also uses (future parity): `set_cwd`, `side_question`, `mcp_set_servers`, `mcp_authenticate` / `mcp_clear_auth` / `mcp_oauth_callback_url`, `channel_enable`, `reload_skills`, `reload_plugins`, `message_rated`, `submit_feedback`, `claude_authenticate` (+oauth), `seed_read_state`, `ultrareview_launch` (vsix).
- `generate_session_title {description, persist:false}` → `.title`. The extension fires it at the first user send with the message text; chimaera does too, and the result feeds the workbench naming chain as an ai-title (Pass 4).
- `mcp_status {}` → `{mcpServers:[{name, status: connected|failed|needs-auth|pending|disabled, scope, config, error?, tools:[{name, annotations}]}]}` (the extension filters its own IDE server out). `mcp_toggle {serverName, enabled}`, `mcp_reconnect {serverName}`, `mcp_authenticate {serverName, redirectUri}`; params are camelCase (Pass 4).
- `read_file {path, max_bytes?, encoding?, anchor?}`: 2.1.310 documents `anchor` (`@internal`): `workspace_root`, `diff_root`, `repo {repo}`, or `as_written` (gated by `read_file_as_written_v1` in the latest init; the token is new in the 2.1.310 binary, and the probed `-p` init did not list it) for a path copied from one of Claude's replies, which the session resolves against the live cwd, the git root and the files its own file tools have held. Not used: chimaera resolves reply paths itself (Pass 52).
- Since 2.1.307 an HTTP MCP tool call cut off by a closed connection is retried once, and only when the error says the call cannot have run, or the tool's `annotations` say `readOnlyHint: true` or `idempotentHint: true` (changelog; binary, Pass 53). `readOnlyHint` also makes an MCP tool concurrency-safe (it may run beside other calls in a batch) and lets plan mode call it; plan mode refuses every other MCP tool. Default mode still asks unless a rule allows the tool. Chimaera's nine read-only tools (`list_terminals`, `read_terminal`, `document_guide`, `check_document`, `workspace_status`, `list_changed_files`, `read_timeline`, `workspace_agents`, `read_agent`) carry `readOnlyHint: true`; `update_plan` (a level-set) carries `idempotentHint: true`; `read_messages` says it is neither, because it settles what it shows and a retry after a lost answer would read "No messages waiting" (`mcp.rs` `tool_annotations`, Pass 53).
- `mcp_call {tool, arguments}` exists and calls an MCP tool through the CLI; the elicitation probe uses it (`scripts/probe-claude-elicitation.py`; 2026-10-03, claude 2.1.288).

## The user frame and attachments

- The user-message uuid is client-minted. The extension writes `{type:"user", uuid: crypto.randomUUID(), session_id:"", parent_tool_use_id: null, message:{…}}` to stdin; the driver does the same, so every send has a checkpoint anchor before any frame returns (Pass 4).
- A stdin `user` frame may carry `priority: "now" | "next" | "later"`. Absent means `"next"` (Pass 38, claude 2.1.283). See [Mid-turn messages](#mid-turn-messages-queue-send-now-cancel).
- File mentions ride the prompt text: `@{rel}`, `@{rel}#L{a}-{b}` (also `#{a}-{b}` and `:{a}`). Selection context is a separate text block: `<ide_selection>The user selected the lines {a} to {b} from {path}:\n{text}\n\nThis may or may not be related to the current task.</ide_selection>`. Terminal grabs are `<terminal name="N">…</terminal>` blocks. Images are standard base64 image blocks; text files are `document` blocks with `title` (Pass 3, vsix).
- A sent image's saved copy is daemon-side only: `ContentBlock::Image.path` and `UserMessage.attachment_paths` ride the echo, and the stream-json `image` block the CLI gets is byte-identical to before (Pass 37, claude 2.1.283). See [cross-agent.md#sent-images](cross-agent.md#sent-images).
- `UserPromptSubmit` does not fire for stdin `user` messages. Anything that hung off that hook (first-prompt capture, `@term:` autolink) runs off the protocol's own input path in chat mode (original probe).

## Slash commands

- The extension hardcodes no command list: the palette mirrors the CLI's catalog (`claudeConfig.commands`, each `{name, description, argumentHint, aliases}`; a plugin duplicate invokes through a namespaced `plugin:name` alias). Everything is sent as `/name` prompt text except `/remote-control|/rc` (a client-side toggle) and `/context` and `/usage` (native panels). Slash sends bypass the message queue (Pass 2, vsix).
- Command results round-trip as user-message text wrapped in `<local-command-stdout>` / `<local-command-stderr>` (Pass 2, vsix). `system/local_command_output {content}` carries a local command's output with those wrappers; chimaera shows it as a Notice with the wrappers stripped (Pass 30, claude 2.1.259).
- A local command such as `/goal` answers with a `<synthetic>` assistant frame carrying `local_command_run {command, args}` and `local_command_source` (Pass 47, claude 2.1.300).
- The extension's permission-mode cycle is `default → acceptEdits → plan` (+ `auto` when `autoModeAvailability` is `"available"`); its thinking toggle is `setThinkingLevel("off"|"default_on")` (Pass 2, vsix).
- `/advisor <model>` sent as a stream-json message persists `advisorModel` to the user's `~/.claude/settings.json`, as the TUI does, and changes every Claude Code session on the machine. Probe it only against a throwaway HOME (Pass 33, claude 2.1.283).

## Turn lifecycle and the stream

- A turn opens lazily through `ensure_turn` on its first real stream, assistant or tool frame. A frame that arrives with `turn_active == false` opens an implicit turn, so a wrong assumption degrades to a correct boundary instead of a phantom turn (Pass 2; Pass 11).
- `on_result` captures `was_active` before clearing the turn. It emits the turn end (`TurnCompleted` on success, `TurnAborted` on `is_error`) and the once-per-turn `get_context_usage` refresh only when `was_active`. A bare result that opened no turn emits no phantom turn end (Pass 11, claude 2.1.206).
- `system/status {status, permissionMode?, compact_result?, compact_error?}`: `status:"requesting"` at turn start (Pass 30, claude 2.1.259). CLI-initiated mode changes (plan exits, applied `setMode` suggestions) ride `permissionMode` (Pass 6, vsix).
- Compaction starts with `status:"compacting"` and settles with `status:null` plus `compact_result:"success"|"failed"`; a failure also carries `compact_error`. `system/compact_boundary {compact_metadata:{trigger, pre_tokens}}` marks a successful auto or manual compaction and completes the same lifecycle; the overlapping success status is deduped. Both map to the shared journaled `ContextCompaction` lifecycle, and the UI keeps the token count in its completion notice (Pass 6, live-verified at claude 2.1.212 with manual `/compact`). Manual `/compact` lands the boundary first; a 2.1.310 auto-compaction lands `compact_result: success` 4 ms before `compact_boundary {trigger: "auto", pre_tokens, post_tokens, …}`, so the driver holds the success status until the boundary (or the next content frame) to keep `pre_tokens` (Pass 53).
- Idle compaction (2.1.302's `idleCompaction` setting, default on) never opens a turn under `-p` (Pass 53, binary + live probe, claude 2.1.310). The timer fires at 90 % of the prompt cache's TTL after the last activity (`fireAtFraction` 0.9, clamped 0.5–0.95; a fire more than 60 s late is dropped), only for the 1-hour cache (`tengu_sunny_locket`) or a cache keepalive (`tengu_bubbly_canyon`), and only above `minTokens` (200 000 by default; `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`, floored at 100 000). Its mode is a server flag: `compact` compacts in place through the REPL's host, which only the interactive `SessionController` sets, so under `-p` it ends `no_host`; `compact_on_return` (the probed account's mode) precomputes a summary in the background (wired for the `sdk` query source too) and swaps it in at the start of the next turn, inside that turn's own autocompact, followed by a notice "Compacted using a summary written while you were away · turn off with "idleCompaction": false in settings.json". So the swap rides a turn a message opened, and its frames are that turn's compaction (see the probe in [passes.md](passes.md), Pass 53).
- Switching to a model with a smaller context window (2.1.30x "a conversation too long for the new model is now summarized by the previous model first"; 2.1.301 "without asking first" fixed) is a compaction inside the next turn's own autocompact, not a separate turn: before the first request, if the last assistant message's `requestedModel` has a larger window than the new model and the context would be `blocked` there, the CLI compacts with that previous model (`compact_larger_model`), then answers on the new one (binary, Pass 53). It streams the ordinary `status: compacting` → `compact_boundary` lifecycle inside the turn the next message opened, which the driver already maps to `ContextCompaction`; `set_model`'s ack is still the `ModelSwitched`. Every first-party model in the 2.1.310 catalog (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1) has a 1M window, so a switch inside the catalog never triggers it; an explicit older id (`claude-haiku-4-5`, 200 000) does.
- Text-block boundaries carry the paragraph break. One assistant message routinely holds several `text` blocks (interleaved thinking splits them), and the model never re-emits `\n\n` across the boundary: concatenating `content_block_delta` text verbatim renders `…prose.#### Heading` as one line. `Coalescer::break_paragraph` (model.rs) marks the break at a block boundary and materializes `\n\n` with the next non-empty text of that kind in that turn's scope: a scope's first block never opens with one, empty blocks and interrupts never dangle one, and a turn opened out of band (an idle send, a queued flush) never inherits one. Claude marks at `content_block_start` (text and thinking) and per block on the complete-`assistant` fallback. The transcript importer applies the same rule to seeded history, and the UI reducer trims a separator that lands at the start of a new transcript block (original probe).
- `system/thinking_tokens {estimated_tokens, estimated_tokens_delta, user_message_uuid, uuid}` (the `user_message_uuid` seen at 2.1.310, Pass 52) fires during thinking even when the display is summarized and no `thinking_delta` streams. The driver maps it to `ThinkingTokens`, throttled to every ~256 tokens; the status row shows "thinking · ~N tokens" (Pass 5).
- Each API call's `message_delta.usage.output_tokens` (per call; the result's total is their sum) plus the running thinking estimate become `AgentEvent::TurnTokens {output}` (Pass 31, claude 2.1.281).
- The `stream_event` wrapper carries `thinking_display: "updates"` on `message_start` and on thinking blocks (Pass 33, claude 2.1.283). Not consumed.
- A per-block `assistant` frame whose one block is a streamed thinking block carries the wrapper fields `thinking_display` and `thinking_duration_ms` (`@internal`, display only: `content_block_start` to `content_block_stop`; absent on replayed history). Not consumed (Pass 52, claude 2.1.310).
- `result` gains `model_usage_since_last_result` (a per-model usage map since the previous result) at 2.1.310. Not consumed (Pass 52).
- `result` frames carry `user_message_uuid(s)` naming the messages the turn read (Pass 38). The driver uses the list only as a backstop for a `command_lifecycle started` that never arrived.
- `result.usage.output_tokens_details.thinking_tokens`, `service_tier`, `inference_geo` are not consumed (Pass 30, claude 2.1.259).
- `system/post_turn_summary {summarizes_uuid, status_category, status_detail, needs_action}` maps to the additive `SessionStatus {category, detail, needs_action}`, folded latest-wins into `ChatInfo` (`status_detail` / `status_category` / `status_needs_action`). The flag clears on `TurnStarted`; the line stays as context; `needs_action` raises the `idle_prompt` attention state on top of `finished` (the frame follows the `result`). `summarizes_uuid` is dropped (Pass 17).
  - `needs_action` is a string, not a bool: `"needs_action": ""` means nothing is needed. The driver maps truthiness (a non-empty string, or a literal `true`) (Pass 17, claude 2.1.207).
  - Emission is conditional and version-unstable: it fired after workflow turns on 2.1.207, never on 2.1.211, and again on a plain echo turn on 2.1.259 (`status_category: "review_ready"`, `status_detail: "starting task execution"`). Nothing may depend on it arriving (Pass 17; Pass 30). The extension routes the subtype but never consumes it.
- An empty `result` after a resume: when the previous process was SIGTERMed while a `run_in_background` Bash ran, the resumed process answers the first send with `system/init`, a `result` with `num_turns: 0`, `duration_ms` ≈ 25, `duration_api_ms: 0`, `stop_reason: null`, `usage.iterations: []` and the previous `total_cost_usd`, then a second `system/init` and the real turn. The CLI found the background shell had no completion record and queued its own `<task-notification>…<status>stopped</status><summary>Background shell command didn't finish before the previous session ended</summary>…`, which the first send drains without an API call. That notification never reaches stdout; the model sees it in the next turn. A clean resume shows no empty result. Only Bash was probed. The driver maps the empty result to an empty completed turn before the real one (Pass 32; Pass 33, claude 2.1.283).

## Mid-turn messages: queue, Send now, cancel

The current model: a message sent mid-turn is read at the agent's next step. ⌥↩ sends one for after the turn. Every waiting bubble has Send now and ✕ (Pass 38, claude 2.1.283; Send now amended 2026-10-05, claude 2.1.289).

CLI facts (Pass 38, claude 2.1.283, unless noted):

- `{type:"command_lifecycle", command_uuid, state}` is emitted on stdout with no opt-in, gated by `msg_lifecycle_v1` (Pass 30). States: `queued | started | completed | cancelled | discarded | refused`. For a stdin frame with a `uuid`, `started` is the moment the model reads it. A folded message emits `completed` before its turn's `result`; a turn opener emits it after. A message consumed by an aborted turn reports `cancelled` after `started`: it was read; do not re-send.
- `next` is read mid-turn. Two messages written during `sleep 8` got `queued` at once and `started`, back to back, when the tool result landed. The agent answered in the same turn: one `result`, `user_message_uuids: [A, B, C]`.
- `later` waits for the turn. Then every waiting message starts together as one turn: `started` B, C right after A's `result` and before the next `system/init`; the new turn's frames carry `user_message_uuid: C`, `user_message_uuids: [B, C]`.
- `interrupt` keeps the queue. It answers `{still_queued: [B, C], cancelled: […]}` (`interrupt_receipt_v1`, Pass 30). The aborted turn's result is `error_during_execution`, `terminal_reason: aborted_tools`; then A `cancelled`; then B and C `started` together as the next turn. `cancel_queued: true` sweeps them instead; unused.
- `cancel_async_message {message_uuid}` withdraws a queued message: `command_lifecycle cancelled` lands first, then `{cancelled: true}`. After the agent took it, the answer is `{cancelled: false}`. It un-queued reliably at 2.1.206 too (Pass 12 live probe `claude_cancel_async_message_behavior`: one turn completed, the cancelled message never ran).
- `priority: "now"` sent 0.5 s into a `sleep` aborts the tool at once (`terminal_reason: aborted_tools`, an empty `result`) and runs as a fresh turn. Sent after the Bash became a task (`task_started`), it waits for the command to finish instead of backgrounding it, and the other queued message folds into the new turn. Re-sending a queued message under its own `uuid` with `"now"` (after `cancel_async_message`) is silently dropped as a duplicate. There is no promote-in-place control request.
- A plain `interrupt` is the CLI's Stop, and a Stop ends background agents: `background_tasks_changed {tasks: []}`, `task_updated {patch: {status: "killed"}}` and `task_notification {status: "stopped"}` for the agent land before the receipt. Every interrupted tool gets "The user doesn't want to proceed with this tool use", in the subagent too. A stopped agent cannot be resumed: `ListAgents` shows it `killed`, and `SendMessage` to it answers `{"success": false, "message": "Agent <id> was stopped by the user and won't be resumed. …"}` (2026-10-05, claude 2.1.289).
- `interrupt {send_now: true, message_uuid}` is the terminal's send-now key, advertised as `interrupt_send_now_v1`. The schema text: "It is not a Stop: it makes no later turn start aborted, cancels nothing that is queued, and ends no background task, subscription or other thing outside the running turn that a Stop ends." `message_uuid` is compared as an exact string; the message must already be in the CLI's queue. With `cancel_queued: true` the request is a Stop again; a CLI without the capability treats it as a plain interrupt. The receipt gains `send_now`: `stopped` (the turn was aborted; its result follows), `delivering` (no turn stopped yet; the CLI is moving what the turn waits on to the background, or the message is already on its way; it may still stop the turn later, without a marker), or `nothing_waiting`. Live: receipt `{still_queued: [B], send_now: "stopped"}`, the foreground Bash's `task_notification {status: "stopped"}`, the interruption marker, the `error_during_execution` result, A `cancelled`, B `started`; no frame for the background agent, and `SendMessage` to it afterwards answered `success: true`. Sent in the same instant as the message, it still found the message (2026-10-05, claude 2.1.289).
- `system/turn_preempted {reason:"rapid_followup", preempted_by_uuid, preempted_message_uuids}` needs `rapidFollowupPreempt` on initialize; explicit `now`/`later` never produce it. Not adopted (Pass 31; Pass 38).
- `interrupt_requeue_taken_v1` (2.1.310, `@internal`, input only): a stdin `user` frame may carry `requeue_if_interrupted_within_ms` (1–10000; more counts as 10000). When a Stop without `cancel_queued` stops a turn that is taking the prompt in, within that time of the turn's `system/status requesting` for the request that carries it and before the model's reply begins, the CLI puts the prompt back at the front of its queue instead of losing it with the stopped turn: at most once, only the last prompt taken since the model last spoke, never after the host's own `cancel_async_message` answered `cancelled: false`, and only for a person's own typing (not synthetic, peer, relayed or client-composed messages; a frame with no `client_platform` qualifies). The binary text says the field is for "an interrupt [that] was sent while its sender still believed the prompt was waiting" (Pass 52 schema; Pass 53 binary).
  - Live (Pass 53, claude 2.1.310, haiku): A ran `sleep 6 && echo done` in the foreground; B, written mid-turn with `priority: "next"` and the field at 3000, started 6 ms after the tool result, and a Stop sent the same instant (`interrupt {for_user_message_uuids: [A]}`) crossed it. Frames: `started` B → `system/status requesting {user_message_uuids: [A, B]}` → `queued` B (a second time) → the receipt `{still_queued: [B], put_back: [B], turn: "stopped"}` → `[Request interrupted by user]` → `result {subtype: error_during_execution, terminal_reason: aborted_streaming, user_message_uuids: [A]}` → `cancelled` A → `started` B (its own turn, 1 ms later) → `init` → reply "second" → `completed` B. The `queued` frame and the receipt both precede the stopped turn's result.
- `interrupt {for_user_message_uuids}` (2.1.310, `@internal`): one to eight uuids of the user messages whose turn the Stop is for; the current turn is the latest one dequeued for a client's message, with every turn started since. A Stop naming one of its messages (or sent while the CLI knows of no current turn) is a plain interrupt; any other answers `turn: "spared"` and does nothing. "Always include the message that opened the turn." Not read beside `send_now` or `cancel_queued`, nor by older CLIs (which answer without `turn`). The receipt's `turn`: `stopped`, `idle` (no turn under way) or `spared`. Live (Pass 53, claude 2.1.310): after A's turn ended and C's began, a Stop naming A answered `{still_queued: [], turn: "spared"}` and C completed; a Stop naming C's own turn answered `turn: "stopped"` and C ended `error_during_execution`.
- The CLI coalesces rapid queued sends into fewer turns and fewer `result` frames than messages; the count depends on timing; the invariant is "results ≤ queued sends" (Pass 11, claude 2.1.206). This is why delivery is never inferred from counting results.
- The changelog confirms the design: a send-now key "interrupts the current turn and sends all queued messages at once"; later, send now moves running tools to the background instead of cancelling the turn (Pass 38).

Chimaera's mapping:

- With `msg_lifecycle_v1` on the latest init, a mid-turn send is written at once with `priority: "next"` (`"later"` for `SendAfterTurn`) and waits in `awaiting_read`. `command_lifecycle started` resolves it `sent`. Mid-turn it gets no `Checkpoint`; as a turn opener it gets a `Checkpoint` anchored after the finished turn (Pass 38).
- `cancelled` (never started) → `Cancelled` only while chimaera's own `cancel_async_message` for it is in flight (the frame lands before the answer). A cancel chimaera did not ask for (the CLI sweeping its queue) is `dropped`, never a silent vanish. `discarded` / `refused` → `dropped`. Teardown drops what was never read (Pass 38).
- A turn opener's `started` sets `turn_starting` until that turn's first frame. A send inside that gap (seconds long, especially right after Send now) waits instead of opening its own turn (Pass 38).
- ✕ → `cancel_async_message`. An id that already resolved gets a tombstone `Cancelled`: the reducer removes a `dropped` bubble and no-ops for a `sent` one (seq order guarantees `sent` folds first) (Pass 14; Pass 38).
- Send now on a CLI with `interrupt_send_now_v1`, for a message in the CLI's queue, sends `interrupt {send_now: true, message_uuid}`. The interrupt watchdog is armed by a `stopped` receipt, not by the request, because a `delivering` turn keeps running; `nothing_waiting` clears the user-stop flag. A message the driver still holds (pre-init, or an older CLI) gets the plain interrupt, including in the `turn_starting` gap (2026-10-05).
- An aborted turn does not close the row of a backgrounded agent the CLI still lists in `background_tasks_changed`: after a send-now it is running (2026-10-05).
- `AgentCommand::Interrupt` is the CLI's Stop and ends background agents; no request field spares them (2026-10-05).
- `SendIfRunning` (agent-to-agent messages) settles `Dropped` at once without writing: a `priority: "next"` frame that misses its turn would run as the next turn, and `cancel_async_message` can lose that race. The daemon reaches claude through hooks instead (Pass 39, claude 2.1.284). See [Hooks under -p](#hooks-under--p).
- A send made before the first init is held and handed over when init advertises the queue (Pass 38).
- With `interrupt_requeue_taken_v1` (Pass 53): every waiting message is written with `requeue_if_interrupted_within_ms: 2000` (`REQUEUE_WINDOW_MS`: one human reaction time plus the `started` frame's trip to the window and the Stop's trip back over a slow SSH link; longer would put back a prompt the user had watched being read and meant to stop). A send that opens a turn is not: its bubble reads as sent, so a Stop right after it means "stop this". At `started` the message is held as `Taken` (not yet `sent`; the bubble stays in the pending stack) until it can no longer be put back: the first main-thread `stream_event` or `assistant` frame (the reply began), a `result` with no Stop in flight, the window passing (from `started`, restarted by a `requesting` status that lists it), or a Stop receipt that did not put it back. A second `queued` frame or the receipt's `put_back` returns it to `awaiting_read` (front); its next `started` reads it at once, as the rewind boundary of the turn it opens. Only the last message taken since the model spoke can be put back, so a newer one releases the older. ✕ on a taken message asks the CLI (`cancel_async_message`): `cancelled: false` releases it as read. Teardown releases it as read.
- With the same capability, `AgentCommand::Interrupt` sends `interrupt {for_user_message_uuids}` naming the current turn's messages (the opener, then the latest folds, ≤ 8; reset when a message of ours opens a turn, kept across a turn the CLI opens itself, which the CLI counts as part of the current turn). With none known (a turn the CLI opened before any send), the Stop is plain. A `spared` receipt disarms the interrupt watchdog and clears the user-stop flag, so the running turn is never aborted by the watchdog or relabelled as stopped.
- Fallback for a CLI without `msg_lifecycle_v1`: hold-until-flush (Pass 13, claude 2.1.206; amended by Pass 14). A send that arrives while a turn is active is held in `queued_sends` and not written. At every turn end, success or `is_error`, `on_result` writes the whole held batch and resolves each `sent` in one step; the abort marker lands first. The flushed uuids stage in `flushing` until the next frame proves the write shipped (a `WriteFailed` would otherwise strand them "queued"); `drain_pending` drops them. The interrupt watchdog also flushes. `drain_pending` (process death) is the only other `dropped` producer. Flushed messages take their `Checkpoint` at the flush (Pass 38). Accepted edges of the batched flush: grouped ordering (`[q2, q3, resp2, resp3]`), and if the user interrupts the first flushed message the CLI drops its siblings, which stay `sent` with no reply. Known narrow edge: cancelling a held message that is another held message's checkpoint `preceding`, then forking at that successor, resolves the fork anchor to the never-written uuid (needs ≥ 2 held sends with no frame between them); not fixed.

## Asks: permissions, plan approval, questions, dialogs, elicitation

- Allow → `{behavior:"allow", updatedInput, updatedPermissions}`. The "always" button re-stamps `permission_suggestions` with a user-chosen `destination`: `localSettings` ("this project (just you)", `.claude/settings.local.json`), `userSettings` ("all projects"), `projectSettings` ("this project (shared)"), `session` ("this session", unsaved); `cliArg` exists but is not in the cycler. The chosen destination re-stamps every suggestion except `setMode`, which keeps its own. Suggestion types: `addRules`, `addDirectories`, `setMode` (Pass 2; Pass 4, vsix).
- Deny → `{behavior:"deny", message, interrupt:true}` with the directive constant ("The user doesn't want to proceed… STOP what you are doing and wait…"). The CLI aborts the turn with an `is_error:true` result (→ `TurnAborted`). This deny does not set the user-stop flag (Pass 2; Pass 8; Pass 9).
- Deny with feedback → `{behavior:"deny", message: <directive constant> + "\n\nThe user's feedback: " + <reason>, interrupt:false}`. The tool errors (`is_error` tool_result) but the turn runs on and ends with a success result. The driver journals the reason as a `UserMessage`, since the model received it (Pass 9, live).
- `ExitPlanMode` is a plan approval, not a tool permission. It is a `can_use_tool` request with `tool_name:"ExitPlanMode"`; `input.plan` is the plan markdown. The driver maps it to a `PermissionRequest` whose additive `plan` field carries the capped markdown; `input_preview` drops the `plan` key. Options, verbatim and in order: "Yes, and auto-accept edits" / "Yes, manually approve" / "No, keep planning". Approval = `{behavior:"allow", updatedInput}` echoing the input; comments ride `updatedInput.{userFeedback,userComments}` (both, same text; the CLI accepts them). The CLI exits plan mode itself and the change rides `system/status`. "Yes, and auto-accept edits" sends the allow, then `set_permission_mode acceptEdits` in the same step (its ack → `ModeChanged`); the extension instead re-stamps a `setMode` suggestion. "No, keep planning" is the deny path: bare = the directive deny (the model stops, still in plan mode); with comments = the feedback deny, so the model revises at once (Pass 9).
- `AskUserQuestion` is a normal `can_use_tool` request; input `{questions:[{question, header, options:[{label, description?}], multiSelect}]}`. Answer = allow with `updatedInput:{questions (echoed), answers}`, where `answers` is keyed by the question text and each value is the chosen labels joined ", " (free text rides as a label; "Other" is client furniture). Esc = the directive deny. Chimaera renders a QuestionCard and emits no `ToolCall` row for it (Pass 7, vsix; 2026-07-10). `askUserQuestionTimeout` (60s/5m/10m/never) runs CLI-side; unanswered prompts settle by the park deadline (Pass 10).
- `request_user_dialog`: CLI→client `{subtype:"request_user_dialog", dialog_kind, payload (camelCase), tool_use_id}`; answer `{behavior:"completed", result}` or `{behavior:"cancelled"}`. Result strings: overage `consent` | `switch_default`; refusal `retry_fallback` | `edit_prompt`. Outcomes echo later as `model_consent_fallback` / `model_refusal_fallback` (Pass 7, vsix). Unknown dialog kinds are answered `cancelled` with a Notice naming the kind (2026-07-10).
- MCP elicitation: `control_request.request` = `{subtype:"elicitation", mcp_server_name, message, mode:"form"|"url"}`, plus `requested_schema` for forms or `url, elicitation_id` for browser requests. Reply inside `control_response.response.response` with `{action:"accept", content:{…}}`, `{action:"decline"}` or `{action:"cancel"}`. Live (no model): form accept preserved integer zero, boolean false, text and a string array; decline and URL cancel arrived exactly. An MCP array enum's `items` must include `type:"string"`; Claude rejects the malformed schema before asking (2026-10-03, claude 2.1.288). The shared form rules are in [cross-agent.md#mcp-elicitation-forms](cross-agent.md#mcp-elicitation-forms).
- `control_cancel_request` → `PermissionResolved {option_id:"cancelled"}` (2026-07-10). The ask lifecycle rules are in [cross-agent.md#ask-lifecycle](cross-agent.md#ask-lifecycle).
- A repo's own hook layer (for example a destructive-command PreToolUse guard) denies inside the CLI; the wire carries only the failed tool_result, and no card can exist (2026-07-10).
- `system/permission_check_status {tool_use_id, agent_id?, status: "checking" | "done"}` (`@internal`) says a call has waited ~4 s on the auto-mode classifier. Not adopted (Pass 43, claude 2.1.300).

- Hooks fire normally under stream-json through `--settings` HTTP hooks, except `UserPromptSubmit` for stdin messages (original probe).
- `system/hook_started` / `hook_response {output}` arrive without `--include-hook-events`, SessionStart hooks at least (Pass 30, claude 2.1.259). Tolerated after the handshake; before it they feed `startup_progress`.
- A PostToolUse hook's `additionalContext` reaches the model mid-turn under `-p` stream-json; the agent used it in the same turn. Nothing on stdout records the context (no `hook_response` for PostToolUse), so the daemon journals its own `AgentMessage` to show it. Chimaera's `type: http` hooks carry agent messages this way (Pass 39, claude 2.1.284).
- Hooks fired inside a subagent carry the subagent's identity: with an `Agent` call under `isolation: "worktree"`, `SubagentStart`, the subagent's `PreToolUse` / `PostToolUse` and `SubagentStop` all carry `agent_id` + `agent_type` and, as `cwd`, the subagent's worktree (`<repo>/.claude/worktrees/agent-<agent_id>`, branch `worktree-agent-<agent_id>`). The parent's own hooks carry neither field. The daemon takes `cwd` only from payloads without a subagent identity, and answers a subagent's hook with no `additionalContext` of the session's (2026-10-04, claude 2.1.289).

- `ListAgents` / `SendMessage` fire PostToolUse like any tool. `tool_name` is `"ListAgents"` (`tool_input: {}`, `tool_response.listing`) or `"SendMessage"` (`tool_input: {to, summary, message}`). ## Subagents

- The subagent tool is `Agent`; older CLIs named it `Task`. Its input carries `description` + `prompt`; drivers match both names (Pass 3, claude 2.1.207).
- The official client hides `parent_tool_use_id`-tagged transcript frames; chimaera hides them too. The visible surface is the Agent tool row ("Agent: {description}") (Pass 3, vsix).
- `system/task_started {task_id, tool_use_id, task_type, description, prompt, subagent_type}`. `task_type` values: `local_agent` (subagent), `local_bash` (backgrounded Bash or Monitor), `local_workflow`; the binary also names `local_command` and `remote_agent` (Pass 3, claude 2.1.207). 2.1.281 adds `is_backgrounded`, `spawn_depth`, `skip_transcript`, `ambient` (Pass 31).
- `system/task_progress {task_id, tool_use_id, description?, last_tool_name?, summary?, usage:{total_tokens, tool_uses, duration_ms}}` (Pass 4). Progress lines prefer `description` ("Running wc -c") over the bare tool name (Pass 31).
- `system/task_updated {task_id, patch:{status, end_time}}` has patch semantics (Pass 3). 2.1.281 adds `patch.is_backgrounded` (a foreground agent moved to the background), `total_paused_ms`, `error`, and statuses `killed | paused` (Pass 31).
- `system/task_notification {task_id, tool_use_id, status ("completed"|"failed"|"stopped"), output_file, summary, usage:{total_tokens, tool_uses, duration_ms}}` is the close with a verdict (Pass 3). 2.1.281 adds `reason: "worker_restart"` and `resource_links` (Pass 31).
- `task_id` is the subagent's agent id (`a0dd2a5017a275850`), the same id the Agent tool_result prints ("agentId: …") (Pass 42, claude 2.1.289).
- A foreground subagent also closes with `task_notification`, whose `summary` is the agent's clean final report, right before its Agent `tool_result`. That tool_result wraps the report in model-facing scaffolding: `"[Subagent hand-back] … The report follows:\n"` + every report line indented two spaces + `agentId: … (use SendMessage …)` + `<usage>…</usage>`; the frame's `tool_use_result.content` holds the clean report. Agent rows show the report with the hand-back frame stripped, live and on import (Pass 31, claude 2.1.281).
- Every running agent drives `system/task_summary {detail}`, the CLI's spinner phrase ("Counting files"); `detail: null` clears it, after the result too. It maps to `AgentEvent::ActivityLine {detail?}`, latest-wins (Pass 31, claude 2.1.281).
- `AgentEvent::SubagentFinished {id?, label, status, result?, stats?}` is journaled once per subagent from `task_notification`: this turn's agents through `task_rows`, a backgrounded agent that outlived its turn through its `local_agent` lane. A subagent's close never also yields a background-close notice. `stats` reads "2 tools · 12.3k tokens · 4s"; counts use `model::fmt_tokens` ("1 tool", "20.3k tokens", "2.3M tokens") (Pass 31; Pass 43).
- Binding: the driver binds task frames to the spawning tool card by `tool_use_id`, with description matching as the fallback for older CLIs, and synthesizes an "Agent:" row when no Task card matches. The maps wipe on `result`; an errored or interrupted turn first closes still-open rows as failed (Pass 4; Pass 3, claude 2.1.207).
- The served model: every hidden subagent `assistant` frame carries `message.model` (the served id, for example `claude-opus-5-5`, `claude-haiku-4-5-20251001`) plus top-level `subagent_type` and `task_description`, foreground and background alike. The driver emits `AgentEvent::SubagentInfo {id: <tool_use id>, agent_id, model, agent_type}` (latest-wins per row; a nested subagent's frames are ignored) and `BackgroundTask.model` on the `local_agent` lane (Pass 42, claude 2.1.289).
- Fork subagents (`Agent {subagent_type: "fork"}`, which inherit the parent's context and effort) are on by default under `-p` since 2.1.302 (`CLAUDE_CODE_FORK_SUBAGENT=0` turns them off); a subagent's own Agent calls run in the foreground by default there (changelog 2.1.302). - A subagent's own Bash task carries `owned_by_subagent: true` on `task_started` (`task_type: "local_bash"`, `is_backgrounded: false`); the parent's foreground command has no such field (2026-10-05, claude 2.1.289).

- The subagent transcript is a file: `~/.claude/projects/<cwd slug>/<session uuid>/subagents/agent-<id>.jsonl`, beside `agent-<id>.meta.json` (`{agentType, description, toolUseId, spawnDepth, requestShape: "foreground" | "background", requestNonInteractive, model}`, where `model` is the requested alias). The CLI drains its queue (stdin messages, peer messages, its own task notifications) only between main-thread steps. `priority: "now"` and Send now both stop the subagent. ## Background work, Monitor and Workflow

- `background_tasks_changed {tasks:[{task_id, task_type, description}]}` replaces the set; an empty array means none left (Pass 3, claude 2.1.207). It is the sole authority for set membership. `task_started` only enriches an already-adopted entry (`workflow_name`, `tool_use_id`) and is ignored for an unknown id (Pass 23, claude 2.1.212).
- A long-running foreground Bash emits a `task_started` identical in shape to a backgrounded one (`task_type: "local_bash"`, same keys). Only membership in a `background_tasks_changed` set tells them apart; a fast command emits none (Pass 23, claude 2.1.212). Every transition into background work, Ctrl-B included, is announced by a set change. A non-`local_agent` `task_started` routes away from the subagent lane and never synthesizes an "Agent:" row.
- Order (Pass 3, claude 2.1.207; documented explicitly at 2.1.300, Pass 43): at spawn the set with the task arrives just before `task_started`. At settle: `background_tasks_changed {tasks:[]}` → `task_updated {patch:{status:"completed", end_time}}` → `task_notification {status, summary, output_file}` — then a fresh `system/init` and a bare no-turn `result`. The 2.1.300 schema text says a finishing task leaves the set after its `task_updated` and `task_notification`. Either way the driver parks a removed-but-unverdicted task in a bounded departed buffer (`departed_background`) and folds the close from the notification, the only frame with `summary` and `output_file`. No `task_progress` fires for a background Bash. Tasks gain `parent_task_id` at 2.1.300.
- `stop_task {task_id}` is generic over the task registry (local_agent, local_bash, remote_agent, …; "Unsupported task type" otherwise). `not_found` / `not_running` are acked as success (`{}`), so a stop racing the task's own finish is harmless. The kill emits `task_notification {status:"stopped", summary: <the description>, output_file}`; a natural finish says `"Background command \"…\" completed (exit code 0)"`. The tray's kill button sends the native task_id through `stop_task`; no separate shell-kill control exists (the `{task_id, shell_id}` shape seen in earlier mining is registry-internal state) (Pass 3, live claude 2.1.207).
- `background_tasks {tool_use_id?}` → `{backgrounded}` backgrounds a running tool call (Ctrl-B parity): with `tool_use_id` that one task, without it every foreground Bash and subagent. Each backgrounded call returns a "running in the background" tool_result at once and settles later through `task_notification` (Pass 3; Pass 7). Live: the control → `background_tasks_changed {tasks:[{local_bash, …}]}` → "tool moved to the background" notice → later the settle (Pass 23, claude 2.1.212).
- The background lane feeds the normalized `background_tasks` level-set and the chat's background tray (Pass 3).
- `Monitor` rides the `local_bash` lane (`task_started {task_type:"local_bash", tool_use_id, is_backgrounded:true}`). Its tool_result is "Monitor started (task …, expires in 30s …)"; its close is `task_notification {summary:'Monitor "<desc>" stream ended'}`. Each monitor event is injected into the CLI's own queue as a user message `{origin:{kind:"task-notification"}, content:"<task-notification><task-id>…</task-id><summary>Monitor event: \"<desc>\"</summary><event>tick 1</event>…"}` and wakes the agent into a turn, but that message never reaches stdout, not even with `--replay-user-messages`; a host sees only the unprompted reply (Pass 31, claude 2.1.281).
- `ambient` on tasks and set entries: "Ambient/housekeeping task. Consumers should hide this from the inline transcript; it may still appear in a tasks panel" (Pass 31). `BackgroundTask.monitor`, `BackgroundTask.ambient` and `BackgroundTaskClose.monitor` are serde-defaulted. An ambient or `skip_transcript` close journals no close entry; `killed` is terminal. The UI titles closes with the CLI's sentence and marks a turn that opens with no user message ("Woke on a monitor event · “build log”", "Resumed on its own") unless a finished row shows the cause.
- `Workflow` (the ultracode prompt keyword, or the tool) is a background lane end to end. The tool_use (input `{script}`) returns at once with launch text ("Workflow launched in background. Task ID: … Transcript dir: … Script file: …"). Frames: `background_tasks_changed {local_workflow}` → `task_started {task_type:"local_workflow", workflow_name (the script's meta.name), prompt:<the script>}` → `task_progress`× → the settle triple (Pass 15, claude 2.1.207; order re-verified Pass 23, claude 2.1.212).
- `task_progress.workflow_progress` is an array of `{type:"workflow_agent", index, label, agentId, model, state ("start"|"progress"|"done"|"error"), startedAt, queuedAt, attempt, promptPreview, lastProgressAt}` plus, once done, `{tokens, toolCalls, durationMs, resultPreview}`. Some ticks omit the array. An agent with no label gets `{meta.name}:{index}`. A workflow whose every agent errors still closes `status:"completed"`. Inner workflow agents' permission requests ride the ordinary `can_use_tool` path (Pass 15, claude 2.1.211).
- Chimaera folds `workflow_name` + `workflow_progress` into the `background_tasks` level-set: per-task agents capped at `WF_AGENTS_CAP` (24, newest kept), a set-wide `WF_AGENTS_SET_BUDGET` (96) that sheds the oldest tasks' dot rows (an over-256 KiB journal entry is replaced by an Error, which would wipe the tray), `agents_total`/`agents_done` over the whole wire list, re-emitted on state transitions only. An explicit `workflow_progress: []` never wipes folded state. A trailing progress frame racing the settle patches the parked task silently. "N/M agents done" ticks and a final `workflow "name" {status} · done/total agents · elapsed` line land on the Workflow card through `tool_use_id`; teardown lands `workflow "name" interrupted · N/M agents`. A whitespace-only `workflow_name` counts as absent. Driver elapsed has an hours rung ("1h 20m 00s") (Pass 15).
- The `/workflows` panel is TUI-only; the extension has no equivalent (Pass 5).
- The Bash result's `backgroundEndsWithFinalResponse` also covers a headless session that takes no further input (Pass 43, claude 2.1.300).
- Background command time limits apply to `-p` / SDK, CI and cloud sessions; chimaera chats use that protocol. Live: `sleep 15` with `run_in_background: true`, `timeout: 1000` produced a stopped task notification after 1.009 s with the native time-limit explanation, then an empty background set. The default 30-minute and maximum 2-hour limits were source-inspected, not waited through (2026-10-03 changelog; 2026-10-04, claude 2.1.289). Chimaera does not impersonate the desktop entry point or disable that policy; durable services belong in a daemon-owned terminal or a scheduler job.

## Task list

- `TodoWrite` (older CLIs) carries the whole list on every call. The incremental family `TaskCreate` / `TaskUpdate` / `TaskList` / `TaskGet` replaced it; the driver holds the list (`TaskTracker`) and re-emits it whole as `AgentEvent::Plan`, so the client reducer stays a replace (Pass 22, claude 2.1.212).
- Task ids exist only in the result text:

| Call | Input | Result |
|---|---|---|
| `TaskCreate` | `{subject, description, activeForm?}` | `Task #1 created successfully: Alpha step` |
| `TaskUpdate` | `{taskId, status?, subject?, description?, activeForm?, owner?, addBlocks?, addBlockedBy?}` | `Updated task #1 status` (the field name varies; `deleted` for a delete) |
| `TaskList` | `{}` | `#1 [in_progress] Alpha step` / `#2 [pending] Beta step (scout)` / `#3 [pending] Gamma step [blocked by #1, #2]` |

- A create is held pending until its result lands, and an update applies on its result, so a failed call never mutates the view. Ids are assigned in creation order from `1`, the fallback when a create result is unparseable.
- `TaskList`'s result is the only full-state level-set and the only way a resumed session recovers its list. It resyncs ids, status and blockers; subject, description and owner keep the values from tool inputs.
- The harness reports only open blockers: a completed blocker drops out of `[blocked by …]` and deleted tasks vanish. Accumulated `addBlockedBy` is filtered against still-open tasks at snapshot time.
- `TaskStop` / `TaskOutput` are background-lane tools keyed by `task_id` and render as ordinary rows.

## Narration and tool labels

- Narration is prose shipped as a thinking block. Opus 5.5 (at least) can emit the prose between tool calls as a `thinking` block. The block kind is a tag inside the `signature` envelope: base64 → protobuf field 2 → field 1 → string field 8, `"narration"` vs `"thinking"` (live signatures decode to `…B\tnarration…` / `…B\x08thinking…`). The CLI's own classifier (`dne` / `$Rt` in 2.1.281) walks that path, fail-closed; 2.1.259 has the classifier but not the wrapper field. 2.1.280+ also names them on the assistant frame's wrapper: `narration_block_indexes: [i…]` ("…give those ordinary thinking treatment" for a listed block with empty text), plus a VS-Code-only `narration_hint: hidden|faint`. Interim prose still sometimes arrives as a normal `text` block; both occur in one turn (Pass 31, claude 2.1.281).
- Stream order for a burst: `content_block_start {thinking, signature:""}` → every `thinking_delta` in one ~10 ms burst → `signature_delta` (the tag) → the per-block `assistant` frame (with `narration_block_indexes`) → `content_block_stop`. Ordinary summarized thinking streams over seconds before its signature (Pass 31). The order is not guaranteed for a narration block that streams longer (Pass 43 addendum, claude 2.1.291).
- The driver holds a streaming thinking block's text outside the coalescer until it is classified: by `signature_delta`, else by the per-block frame (`narration_block_indexes`, else the decoded signature), else at `content_block_stop` (thought). A block still streaming after `THINKING_HOLD_TICKS` (3 ticks, ~300 ms after its first text) or past `THINKING_HOLD_MAX` (8 KiB) flows as thought. Narration joins the message stream with its own paragraph break; reasoning the thought stream. Turn ends, the interrupt watchdog and teardown release a held block as thought. The non-streamed assistant path and the transcript importer classify the same way (Pass 31).
- A narration verdict that arrives after release retracts the thought: the driver keeps the text of a block released as thought while still undecided (bounded at 64 KiB, `RELEASED_THOUGHT_MAX`) until the next block starts or the turn ends. A narration verdict from `signature_delta` or the per-block frame (before or after the stop) emits `AgentEvent::ThoughtRetracted { turn_id, utf16_len }` and then the same text as `MessageChunk`s; later deltas follow as prose. Clients cut `utf16_len` UTF-16 units off the turn's trailing thought row. Past the bound the thought copy stays and the frame's text is emitted as prose. A late narration frame with nothing to retract still emits its text as prose unless that block's text already reached the prose stream (a per-turn set of block-text hashes). A block with no narration signature that closes with no frame stays a thought (Pass 43 addendum).
- `{type:"tool_use_summary", summary, preceding_tool_use_ids[], uuid, session_id, timestamp?}` is a small-model past-tense label for one tool batch ("Listed files in directory"). It is emitted only when the host sets `CLAUDE_CODE_EMIT_TOOL_USE_SUMMARIES` (the CLI's `gates.emitToolUseSummaries`; the Claude desktop app sets it behind a feature gate), only for the main thread (`!agentId`), and about one model round late. Each label costs one small-model call on the user's account. It maps to `AgentEvent::ToolSummary {summary, tool_ids}` (capped); the UI titles a tool group with its labels and counts the unlabelled tail (Pass 31, claude 2.1.281).
- The tool family the driver titles (Pass 30, claude 2.1.259): `Agent`, `Skill`, `Workflow`, `ToolSearch`, `MCPSearch`, `Monitor`, `Sleep`, `ScheduleWakeup`, `SendUserMessage`, `SendUserFile`, `SendMessage`, `ListAgents`, `ReportFindings`, `Artifact`, `CronCreate/Delete/List`, `EnterWorktree` / `ExitWorktree`, `RemoteTrigger`, `PushNotification`, `SuggestSkills`, `DesignSync`, `TeamCreate/TeamDelete`, `Config`, `PowerShell`, `LSP`, `TaskOutput/TaskStop`, `ReadMcpResourceTool/ReadMcpResourceDirTool/ListMcpResourcesTool`, `mcp__<server>__<tool>`; 2.1.300 adds `SubagentHandback` and keeps the rest (Pass 43). `tool_kind` routes PowerShell → Execute, the search tools → Search, the MCP resource readers → Read. `tool_title` composes `Skill: /name args`, `Workflow: <meta name>`, `SendUserFile: a (+N more)`, `ScheduleWakeup: in 20m 00s · reason`, `ReportFindings: N findings`, `SendMessage → to: text`, `tool (server)` for MCP tools. `tool_locations` adds `files[]` (SendUserFile) and `filePath` (LSP). ListAgents, ExitWorktree, CronList and DesignSync keep a bare name.
- 2.1.300 tool parameters: `Agent.effort` (low…max or an integer), `Read.allow_large`, a character offset for `WebFetch`; agent definitions gain `autoCompactWindow`, `omitClaudeMd`, `effort`. None changes a derived title, kind or location (Pass 43).
- An execute `ToolCall` carries the additive `command` (the full command, clipped head+tail to `COMMAND_CAP`, 8 KiB, by `clip_command`). Claude prefixes every Bash call with `cd "<absolute cwd>" && …`, which alone overflows the ~120-char title (Pass 36, claude 2.1.283).
- Assistant frames carry `timestamp`, `request_id`, `wire_tool_inputs`, `tool_use_meta` (MCP display names and icons), and on subagent frames `subagent_type` / `task_description` (Pass 31, claude 2.1.281). Not consumed.
- `system/informational {content, level: info|notice|suggestion|warning, tool_use_id?, prevent_continuation?}` is the CLI's host-facing notice (hook "X says:" lines, pending model switches). Every level but `info` becomes a Notice (Pass 30, claude 2.1.259).
- `prompt_suggestion {type, suggestion}` is an idle-composer suggestion; chimaera shows a click-to-insert chip, cleared on send (Pass 7, vsix).

## Remote Control

- Request (desktop bundle and CLI, identical): `{"subtype":"remote_control","enabled":true,"name":"chimaera · repo","keep_session_on_exit":false}`. `reattach_session_id` and `work_secret` are the desktop's own plumbing and are not sent (Pass 30, claude 2.1.259).
- Live round trip from a plain `-p --input-format stream-json` process (Pass 30, claude 2.1.259):
  1. `system/bridge_state {state:"ready", uuid, session_id}`, before the ack;
  2. the ack `{session_url:"https://claude.ai/code/session_01…", connect_url:"https://claude.ai/code?environment=", environment_id:"", bridge_epoch:1, bridge_session_id:"cse_01…"}`, plus a `background_tasks_changed {tasks:[]}` re-announce;
  3. `system/bridge_state {state:"connected", bridge_epoch:1}` 0.2 s later;
  4. `{subtype:"remote_control", enabled:false}` acks with `response: null` and emits no bridge frame within 5 s.
- The `bridge_state` word is an open set (`ready`, `connected` seen; the code also spells `detail`). Refusals are the CLI's own sentences: "Remote Control is only available with claude.ai subscriptions. Please use `/login`…", "…disabled by your organization's policy…", "…not available inside a cloud session", "…cannot be enabled from inside a remote session". `--sdk-url` is reserved for Anthropic's bridge workers.
- Mapping: `AgentCommand::SetRemoteControl {enabled, name?}` → the request. `AgentEvent::RemoteControl {state: off|connecting|connected|error, session_url?, name?, detail?}` (latest-wins) journals the optimistic Connecting, the ack (link), every `bridge_state` transition (unknown words become a Notice), the refusal (Error + the sentence), and Off at teardown; the bridge is process-owned. `Init` carries the offer flags and a `remote_control: {state, session_url?, name?}` snapshot, because claude re-emits `system/init` mid-process and every consumer resets on Init; a fresh process journals no snapshot. `ChatInfo.remote_control_url` folds the link for the rail. `keep_session_on_exit` stays false so no claude.ai row outlives the driver (Pass 30).
- A `bridge_state disconnected|error` keeps the live record: the CLI reconnects on its own and the session is the same, so the link and name are kept and re-emitted on `connected`. A stray Off/Error word with nothing live is ignored; repeats dedupe. The "Remote Control connected — pick this session up … at <url>" line and a refusal's sentence are driver-journaled Notices (Pass 30 review hardening).
- Naming: callers pass the bare session name (the UI its display name, not `session.name`, which on a chat row is the agent kind; the daemon "<display name> (<4-char id>)" at start); the driver spells `chimaera · <name>`, capped. The server's `control_only_switch_journal` admits `RemoteControl` lines. `SpawnSpec.remote_control = Some(name)` (from `chat.remoteControlAtStart`) enables it right after the handshake, only for spawns that create a chimaera session (`ChatRecipe.remote_control_at_start`: fresh, resumed from recents, resurrected); a view-switch or rewind respawn keeps the user's off (Pass 30). A restart restores the bridge through the carryover (Pass 32).
- Bridge-injected messages (unverified end to end): a message typed on a phone enters the CLI's own queue (`onInboundMessage` → `bridgeOrigin:true`) and never crosses stdin. A text `user` frame that is not a replay, carries no tool_result, has no `parent_tool_use_id`, is not `isMeta` / `isCompactSummary` / `isSynthetic`, passes the importer's `user_prompt_text` filter (command markup, the `Caveat:` preamble) and is not a `[…]` marker, and whose uuid chimaera never minted is treated as remote while the bridge is Connected: `UserMessage {origin:"remote"}`. Whether the CLI emits such a frame for a phone-sent message is not probed (Pass 30; Pass 47).

## Checkpoints, rewind and branches

- Checkpoint key = the user-message uuid (client-minted). `rewind_files {user_message_id, dry_run}` → `{canRewind, filesChanged[], insertions, deletions, error?}` restores files on the live channel with no restart; the dry run feeds the confirm dialog (Pass 4).
- Checkpointing is off under `-p` unless the spawn env carries `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true` (the SDK's `enableFileCheckpointing` option); without it every `rewind_files` answers `{"canRewind":false,"error":"File rewinding is not enabled."}`. Checkpoints track the file tools (Write/Edit) only: a Bash-created file reports `filesChanged:[]` and survives the rewind (Pass 4). Since 2.1.309 `sed -i` is an ordinary Bash command too (it used to be simulated as a file edit), so its edits are no longer restored (changelog 2.1.309; Pass 52).
- The conversation side forks: `--resume <source> --fork-session --resume-session-at <uuid>`, where the uuid is the message preceding the selected user message (inbound assistant/user frames carry `uuid`; the driver tracks the last one). The fork excludes the selected message; `rewind_files` uses the selected message's own uuid (Pass 4, live-verified).
- A non-destructive branch (`POST /api/v1/sessions/{id}/fork`) uses the same native path: a delivered user message's checkpoint carries its own uuid and the preceding uuid; branching from a user message resumes at `preceding_uuid` and restores the text as an unsent draft. Branching after an assistant response is portable, because the normalized assistant block does not expose its native uuid. No transcript is resent on a native branch (Pass 24). The portable handoff is in [cross-agent.md#conversation-branches](cross-agent.md#conversation-branches).
- A mid-turn message gets no `Checkpoint`; a turn opener gets one anchored after the finished turn (Pass 38).

## Loops and goals

Recorded at claude 2.1.300 (Pass 47).

- `/loop <prompt>` with no interval: the bundled skill calls `ScheduleWakeup {delaySeconds 60–3600, reason, prompt, noop}` each tick. Result: `tool_use_result {scheduledFor (epoch ms), clampedDelaySeconds, wasClamped}`; the text says "Next wakeup scheduled for 17:00:00 (in 63s)". Claude rounds up to the next minute; `scheduledFor` is the truth. A wakeup fired ~3 s before it.
- `ScheduleWakeup {stop: true}` → `{scheduledFor: 0, clampedDelaySeconds: 0, wasClamped: false, stopped: true, cancelledWakeups: N}`; it ends a dynamic loop only (a fixed-interval loop "is NOT stopped by this call — cancel it with CronDelete").
- `/loop 1m <prompt>`: `ToolSearch select:CronCreate`, then `CronCreate {cron: "*/1 * * * *", prompt, recurring: true}` → `{id: "f2143f41", humanSchedule: "Every minute", recurring, durable: false, nextFireAt: <float epoch ms>}`. Recurring jobs are jittered by a stable per-job offset (+28.37 s on an every-minute job, +30 min on `17 3 * * *`). The model has sent `recurring: "true"` (a string) and the job still recurred. Jobs are session-only and expire 7 days on.
- `CronList` → `{jobs: [{id, cron, humanSchedule, prompt, recurring, durable, nextFireAt}]}` (the whole set); `CronDelete {id}` → `{id}`.
- A fired wakeup or job opens a turn no message started: `command_lifecycle {state: "started", command_uuid: <unminted>}`, a fresh `system/init`, the turn, `result`, `command_lifecycle {state: "completed"}`. No `user` frame names the trigger.
- 2.1.310 names the trigger on that `started` frame, advertised as `lifecycle_wakeup_source_v1`: `wakeup_source: "loop_wakeup"` (a ScheduleWakeup fire, plus `scheduled_for`, the epoch ms the fire was set for, equal to its call's `scheduledFor`) or `"schedule_wakeup"` (any other scheduled-task fire: a CronCreate job, or the missed-tasks notice; the names match the UserPromptSubmit hook's `source`, so the job word is the counter-intuitive one). A fire removed from the queue unstarted gets only its terminal state. The binary: "A host that keeps an idle session alive for a wakeup should stop waiting only when this equals the time it is waiting for: while this fire sat in the queue, a turn may have armed a newer wakeup, which is still pending." Live: three fires of a `/loop 1m` job each carried `wakeup_source: "schedule_wakeup"` (Pass 52); a direct `ScheduleWakeup {delaySeconds: 60}` (result `scheduledFor: 1792804620000`) fired 92 s later as `started {wakeup_source: "loop_wakeup", scheduled_for: 1792804620000}` with an unminted `command_uuid` (Pass 53, claude 2.1.310). Turns the CLI opens for anything else (a monitor event, finished background work) carry no `wakeup_source`.
- No control request lists, reports or cancels loops. If a tick ends without rescheduling or stopping, the CLI arms one hidden keepalive wakeup (1200 s, budget 1; it logs `[loop] keepalive armed`) with no frame.
- `--resume` restores the session's jobs but not a pending wakeup (a wakeup due 13 minutes after a resume never fired in the resumed `-p` process).
- Durable jobs are not available here: `CronCreate {durable: true}` would write `.claude/scheduled_tasks.json`, gated by the server-side flag `tengu_kairos_cron_durable`, which was off for the probed account ("Session-only (not written to disk, dies when Claude exits)"). The CLI still writes `.claude/scheduled_tasks.lock` `{sessionId, pid, procStart, acquiredAt}`. Chimaera treats every job as session-only and reads neither file.
- `/schedule` (alias `/routines`) manages cloud agents (`RemoteTrigger` over claude.ai's API); each run is its own cloud session and never resumes the chat. Its tool call shows as an ordinary row.
- `/goal <condition>` answers locally ("Goal set: <condition>", `local_command_run {command: "goal", args}`), then the model starts in the same turn. The condition is capped at 4000 characters. The goal is a session Stop hook a small model checks at each stop. A failed check reaches stdout as an `isSynthetic: true` `user` frame `"Stop hook feedback:\n[<condition>]: <reason>"`, and the model goes on in the same turn.
- An achieved or impossible goal never reaches stdout; only the native transcript records it: `attachment {type: "goal_status", met: true, condition, reason, iterations, durationMs, tokens}`, `failed: true` for an impossible one, `met: false` per failed check, `sentinel: true` at set. `active_goal` frames exist in the binary but are not emitted to this host.
- `/goal clear|stop|off|reset|none|cancel` → "Goal cleared: <condition>" (or "No goal set"); bare `/goal` → "Goal active: <condition> (N turns)" plus "Last check: …" or "(not yet evaluated)". Each is a local command that enters the model's context, so the driver never polls it. An interrupted turn leaves the goal set; `--resume` keeps it. `system/notification {key: "stop-hook-block-cap", text}` says the check blocked the stop too often (the goal stays). Claude's words: "Goal achieved", "Goal could not be achieved", "Goal not yet met… continuing".
- Mapping (`autonomy.rs`, fed by `claude.rs`): `Schedule {wakeup?, jobs}` is a level-set of the pending wakeup (`at_ms` = `scheduledFor`, `scheduled_at_ms`, reason, prompt) and session jobs (id, cron, `schedule` = `humanSchedule`, prompt, recurring, `next_at_ms`, `created_at_ms`; ≤ `SCHEDULE_JOBS_CAP`, 50), kept from the tools' calls and structured results (a failed call changes nothing; CronList is the whole truth; a job's next run is computed by `cron.rs`, a 5-field local-time cron with DST-safe stepping). A `command_lifecycle started` for an unminted uuid while idle marks the next turn as the CLI's own, with what the frame said fired it (`autonomy::FireSource`). On a CLI that advertises `lifecycle_wakeup_source_v1` its word is the truth (Pass 53): `loop_wakeup` spends the pending wakeup only when `scheduled_for` is its `at_ms` (an older fire leaves a newer wakeup pending; the turn is still a wakeup, with no reason), `schedule_wakeup` runs the job due soonest (≤ 120 s early) and never touches the wakeup (with none due it is still a job, with no prompt), and no `wakeup_source` is no scheduler fire at all, so a monitor turn never spends a wakeup that happens to be due. An older CLI names nothing, so the earliest item due (a wakeup up to 30 s early, a one-shot job up to 120 s) is taken for the cause. Either way the result is `TurnCause {turn_id, kind: wakeup|job|goal, detail, schedule}` right after `TurnStarted`; nothing due on an older CLI (a monitor, the keepalive) means no cause. `/goal` replies set and clear `Goal {goal?, ended?}`; a synthetic Stop-hook frame whose brackets hold the condition counts a check; a "Goal active" reply adopts a goal the driver never saw set. `stop-hook-block-cap` becomes a Notice. After a turn completes with a goal active, the daemon (`goal_outcome.rs`) reads the transcript tail (≤ 1 MiB, off the reactor, three tries) for the latest `goal_status` and journals `Goal {ended: achieved|failed}`. `ChatInfo.next_wake {at_ms, from_ms, label, count}` and `goal {objective, status}` ride the chat row. Synthetic user frames never read as Remote Control messages. Restart carryover: [cross-agent.md#restart-carryover](cross-agent.md#restart-carryover).

## Stop, teardown and SIGTERM

Recorded at claude 2.1.281 unless noted (Pass 32).

- Claude's Bash tool and Monitor run detached: the shell provider is `{type: "bash", shellPath, detached: true, stdin: "pipe", …}`. Each background command leads its own process group; claude stops a task by signalling its group.
- SIGKILL to claude (the old daemon-exit path, tokio `kill_on_drop`): background commands and Monitors survive, reparented to init.
- stdin EOF: claude does not exit within 10 s. It stops the Monitor, then starts a new, billed turn reacting to the stop; a background Bash survives the later SIGKILL. This contradicts the SDK schema text on `perTaskStopAffordance` ("a one-shot run… closes stdin… still kills hold-back tasks at the held-result release"): an idle interactive session holds no result to release.
- SIGTERM: exit in 0.28 s with status 143, a `task_notification {status: "stopped"}` per task, no new turn, nothing surviving.
- The harness SIGTERMs the child before closing stdin on every stop chimaera initiates (`ChildGuard::terminate`), waits `KILL_GRACE` (3 s), then SIGKILLs. A child that closed its own output is left to exit. A graceful daemon stop runs this for every live chat driver (`chat::stop_all_for_exit`). End to end on claude 2.1.283, the daemon stopped in 0.84 s and the background `sleep` ended with it. A mid-turn claude was not probed; one that ignores SIGTERM past the grace is SIGKILLed and its detached shells survive.
- `--resume` restores the conversation, not its processes; the transcript still holds the agent's own tool results ("Command running in background with ID: bg-1").
- Teardown (`drain_pending`) resolves pending asks `expired`, drops unread messages, fails open subagent rows, lands `workflow "name" interrupted · N/M agents`, and journals Remote Control Off.
