# Codex: app-server JSON-RPC

The current contract of the Codex driver (`src/codex.rs`). The pin is `TESTED_CODEX_VERSION`; the live gate is `just chat-smoke`. Each fact names the pass and the CLI version where it was recorded, for example "(Pass 46, codex 0.162.1)". "vsix" means mined from the official extension bundle (openai.chatgpt 26.5623.141536; 26.623.101652 for Pass 10). "Schema" means the output of `codex app-server generate-ts --experimental` or `generate-json-schema` for that version. "Original probe" means the first live probe (codex 0.142.5). The dated record is [passes.md](passes.md); the shared rules are in [cross-agent.md](cross-agent.md).

## Transport and integration aids

- `codex app-server` speaks JSON-RPC 2.0 as JSONL over stdio, with the `jsonrpc` header omitted (original probe).
- `codex app-server generate-ts --out DIR` and `generate-json-schema --out DIR` emit schemas guaranteed to match that binary. Run one as a free preflight whenever `codex.rs` changes, diff only the relevant v2 types, and keep the generated bulk out of the repository. Schemas cannot prove notification order, whether a notification is conditional, or what a CLI does after cancellation or reconnect; live probes still establish those (audited 2026-07-18).
- Transport ingress is bounded: saturation rejects a request with `-32001` (`Server overloaded; retry later.`), and upstream asks clients to retry with exponential backoff and jitter. Targeted retry is not adopted: it needs idempotency analysis per RPC, hermetic coverage and the billed gate (audited 2026-07-18).
- The connection multiplexes every thread. A spawned subagent's whole transcript (`turn/started`, `item/*`, `thread/tokenUsage/updated`, `thread/status/changed`, `mcpServer/startupStatus/updated`, `turn/completed`) streams on the same connection, told apart only by `params.threadId`. The driver gates every notification on `params.threadId`: absent or matching is the parent's; anything else feeds the subagent lane. `serverRequest/resolved` is exempt, because JSON-RPC ids are connection-scoped. Server→client requests carry the subagent's threadId but answer by rpc id (Pass 16, codex 0.144.2).
- An account-scoped notification (`account/rateLimits/updated`) has no `threadId`, so the thread gate passes it (Pass 46).
- A notification that must belong to a thread but carries none (a malformed `thread/settings/updated`) is rejected, not treated as the parent's (Pass 28).

## Handshake and thread open

- `initialize {clientInfo, capabilities}` → result → the client must send the `initialized` notification → requests (original probe).
- `initialize` must declare `capabilities:{experimentalApi:true}`, or `thread/settings/update` answers `-32600 "requires experimentalApi capability"` (Pass 4, live). The extension also declares `mcpServerOpenaiFormElicitation` and `requestAttestation:false`; chimaera declares neither, because they change frames it does not render (Pass 4).
- `InitializeCapabilities` = `{experimentalApi, requestAttestation, mcpServerOpenaiFormElicitation, optOutNotificationMethods}` (Pass 19, codex 0.144.2), plus `extensions` (Pass 30, codex 0.153.0) and `explicitGatewayOauth` (Pass 33, codex 0.157.1).
- The `initialize` result is `{userAgent, codexHome, platformFamily, platformOs}` (Pass 30, codex 0.153.0). `userAgent` is the server's own phrasing, not a version contract; the handshake discards it. See [cross-agent.md#version-detection](cross-agent.md#version-detection).
- Right after `initialize`: `remoteControl/status/changed`. The handshake keeps it (`HandshakeSideband`) and replays it through the mapper (Pass 30). See [Remote Control](#remote-control).
- `HandshakeSideband` also keeps any server request that arrives while the handshake awaits a response (initialize, thread open, `config/read`, `skills/list`, a revert), in order and up to 16, and replays each through the mapper after the handshake, so it gets a card, an answer or a refusal (Pass 34, codex 0.157.1).
- `config/read {cwd?, includeLayers?}` is always issued, bounded to 2 s, before the thread opens. It echoes `model`, `model_reasoning_effort`, `model_reasoning_summary` (`null` when the user never set one) and `service_tier` (Pass 29; Pass 30; Pass 31).
- `model/list` follows; see [Models, effort and settings](#models-effort-and-settings).
- `skills/list {cwds:[cwd], forceReload:false}` follows `model/list`. Failure or the 2-second timeout is non-fatal; the chat opens without Codex skill rows (Pass 26). See [Skills](#skills).
- `thread/start {cwd, model, approvalPolicy, approvalsReviewer, sandbox, developerInstructions?, …}` → `result.thread.id` (= the sessionId; the rollout lives under `~/.codex/sessions`) (original probe; Pass 20; Pass 26).
- Native `update_plan` requires `config: {"tools.update_plan.enabled": true}` on the thread-open request. The official config schema defaults this tool to disabled; `tools.update_plan=true` is an invalid type. `ThreadStartParams`, `ThreadResumeParams` and `ThreadForkParams` all accept `config`. An app-server launch flag with the correct key appeared in `config/read` but did not expose the tool to the new thread; the same override on `thread/start` produced three native `turn/plan/updated` notifications (inProgress/pending → completed/inProgress → completed/completed), with no Chimaera MCP configured. The driver applies it on start, resume and fork (Pass 48, schema + live codex 0.158.0).
- Codex threads open in the reviewer-assisted default: `sandbox:"workspace-write"`, `approvalPolicy:"on-request"`, `approvalsReviewer:"auto_review"`. The first `Init` reports `auto-review` (Pass 26, codex 0.144.2).
- The `thread/start` result carries `runtimeWorkspaceRoots`, `instructionSources`, `activePermissionProfile`, `multiAgentMode` (default `explicitRequestOnly`), and the effective top-level `reasoningEffort`; the thread object carries `historyMode:"paginated"`, `canAcceptDirectInput`, `agentNickname` / `agentRole`, `source:"vscode"` (Pass 30, codex 0.153.0; Pass 16).
- `thread/start` and `thread/resume` accept an optional `model`. Chimaera carries the launch recipe's model through `SpawnSpec.initial_model` and reads the effective model from the open response, with the requested value as the older-binary fallback; Claude stays argv-configured (Pass 20, codex 0.144.2).
- `thread/start` and `thread/resume` have no `effort` param in the schema: the `effort` the driver puts on the open request is silently ignored (probe: `"high"` requested, settings echo `"xhigh"`, the config default) (Pass 31, codex 0.156.1).
- `thread/resume {threadId, cwd, model, effort}` answers with the rollout's own `reasoningEffort` and ignores the request's `effort`; it does restore the model. After the handshake the driver reconciles: when the conversation's indexed effort differs from the reported one, it sends `thread/settings/update {effort}`, flagged as the handshake's own (not remembered as a preference), and the `thread/settings/updated` read-back settles the header. The same post-handshake replay carries the conversation's permission mode (Pass 30, codex 0.153.0).
- Effort precedence at open (Pass 29, codex 0.144.x): 1. the resumed or forked native thread's last observed parent effort (Chimaera's durable, 200-entry native-thread index); 2. Codex's configured `model_reasoning_effort`, for a new thread or a resumed thread whose legacy journal has no recoverable selection; 3. the app-server's model default. Effort is conversation-local. Init and effort writes are serialized through the index's blocking persistence lane. Only parent `EffortState` events feed the index. For pre-Pass-29 index entries, the first resume migrates once from the journal on a blocking worker, ignoring the bootstrap `EffortState` after every process `Init`.
- `thread/resume` also answers `initialTurnsPage` (null in probes) and a settings echo (approvalPolicy, permissions, reasoningEffort, …) (Pass 10, codex 0.142.5).
- Developer instructions are fixed at a thread's first turn, for good: they are recorded once in the rollout as a `developer` message. On a fresh thread `thread/start {developerInstructions}` replaces an argv `-c developer_instructions` value. A resume with a new argv value or a new `thread/resume {developerInstructions}` keeps the first value (Pass 41, codex 0.157.1). A portable branch's `developerInstructions` therefore works on open and is a no-op on resume.
- `thread/inject_items {threadId, items}` ("Raw Responses API items to append to the thread's model-visible history") answers `{}` and starts no turn. A `{"type":"message","role":"developer","content":[{"type":"input_text","text":…}]}` item is followed on a fresh thread before its first turn and right after a resume, where a newer value supersedes an older one. It emits no item notifications and does not appear in `thread/turns/list` (Pass 41, codex 0.157.1). `SpawnSpec.developer_note` (a cluster job's facts, codex chats only) rides it once the thread opens, after any rewind. Nothing of it is on argv (anyone on a shared node can read argv with `ps`), and the user's own `developer_instructions` stay untouched. A failed inject is logged and the chat opens without it.
- The open request's `developerInstructions` carries a portable branch's bounded transcript on `thread/start`, `thread/resume` or `thread/fork` (Pass 24).
- The handshake reports `startup_progress` (config, thread opening) before `Init` (2026-10-01). See [cross-agent.md#startup-lifecycle](cross-agent.md#startup-lifecycle).

## Startup hooks and delivery confirmation

Recorded at codex 0.159.3 (2026-10-03).

- The schema defines `hook/started|completed {threadId, turnId: string|null, run:{id, eventName, executionMode, sourcePath, status, …}}`. Synchronous `sessionStart` and `userPromptSubmit` hooks can block after `turn/started`, before the native `userMessage` item. The driver shows them as bounded tool rows and in the ActivityLine. Async hooks and other threads must not replace the parent's startup phase.
- Observed live: `turn/started` → `hook/started`, then no completion for over four minutes until interruption. The rollout held repository instructions but not the submitted request; the next turn's "Keep going" was its first recorded user prompt. A successful `turn/start` RPC or `TurnStarted` therefore does not establish delivery.
- The opening `clientId` is tracked until its `userMessage` echo (or, for older runtimes, actual model activity). An interrupt before confirmation emits an explicit resend notice, also when the interrupt watchdog supplies the missing turn end. The notice survives a UI reload.
- For runtimes without a user `clientId`, these confirm receipt: model work items (all tool types, plan and sleep), output deltas, patch updates, `turn/plan/updated`, and parent-turn tool requests. Work notifications must carry the current `turnId`; late frames from a prior turn cannot confirm a new opening message. Setup items (`hookPrompt`, `contextCompaction`) and child-thread activity do not confirm parent delivery. Activity in a turn adopted after a rejected start (or a stale-target steer) cannot confirm an opening message from a different turn; only its exact user echo can.
- Hook ids can be configuration-derived (`session-start:0:<sourcePath>`), so normalized row ids use a local monotonic counter with a random mapper namespace; native hook keys are SHA-256 digests.
- Run statuses `failed`, `blocked` and `stopped` all mean an unsuccessful hook. Diagnostics live in `entries[{kind, text}]` (`error`, `feedback`, `stop`, `warning`); `statusMessage` is a configured progress label. Diagnostics are joined under a byte cap while accumulating; `context` entries, which can contain injected input, are never exposed.
- Isolated reproduction: a trusted project SessionStart hook (`sleep 300`) produced the hook row and phase; Stop produced the resend notice; resending the prompt completed normally.

## Turn lifecycle

- `turn/start {threadId, input, clientUserMessageId, …}` opens a turn (original probe). The full per-turn config: `{threadId, clientUserMessageId, additionalContext, input, environments, cwd, approvalPolicy, approvalsReviewer, sandboxPolicy, permissions, runtimeWorkspaceRoots, model, serviceTier, effort, multiAgentMode, summary, personality, outputSchema, collaborationMode, attachments}` (Pass 2, vsix), plus `turnTrigger`, `toolOutput`, `serviceTierForTurn` (Pass 30, codex 0.153.0) and `parentTurnId` / `rootTurnId` (Pass 43, codex 0.162.1).
- `input` items: `{type:"text", text}`; images as `{type:"image", url:<data URL>}` (or `{type:"localImage", path}` with a shared filesystem; chimaera uses data URLs); `{type:"skill", name, path}` (Pass 4; Pass 26). 0.153.0 adds `audio`, `localAudio`, `mention` (Pass 30). A sent image's saved copy never reaches the agent (Pass 37).
- Every `turn/start` carries `summary: "auto"` unless `config/read` shows the user set `model_reasoning_summary` (Pass 31). See [Reasoning](#reasoning-and-thinking).
- `thread/status/changed {status}`: `active {activeFlags: waitingOnApproval|waitingOnUserInput} | idle | notLoaded | systemError`. Running and attention states derive from turn and request events instead (Pass 7, vsix).
- Notifications on a normal turn (original probe): `thread/status/changed`, `turn/started`, `item/started|completed`, `item/agentMessage/delta {itemId, delta}`, `thread/tokenUsage/updated`, `account/rateLimits/updated`, `turn/completed {turn:{status, durationMs}}`. `thread/started` arrives on the first `turn/start` (Pass 10).
- Turns open lazily on `turn/started`. The driver resets its item trackers on `turn/started` and on the turn-adoption paths. Paragraph breaks are marked on `item/agentMessage/delta`, `item/plan/delta` and reasoning-delta itemId changes plus `summaryPartAdded` sections (original probe; see [claude-code.md#turn-lifecycle-and-the-stream](claude-code.md#turn-lifecycle-and-the-stream) for the shared coalescer rule).
- `TurnStatus` is `completed | interrupted | failed | inProgress`. No `turn/failed` notification exists in the 0.153.0 or 0.156.1 unions; a failed turn is `turn/completed {status: "failed"}` with `Turn.error {message, codexErrorInfo, additionalDetails, misalignment}` ("only populated when the Turn's status is failed"). A failed parent turn maps to `TurnAborted {interrupted: false}`, reason = `turn.error.message` (or "turn failed" when a terminal `error` notification already put the message in the transcript). A failed child turn fails its row. The legacy `turn/failed` arm remains for older binaries (Pass 31, codex 0.156.1). `CodexErrorInfo` also allows a string or an object at 0.162.1 (Pass 43).
- `turn/completed {status:"interrupted"}` follows only a `turn/interrupt` RPC and maps to `TurnAborted {interrupted: true}` with codex's own reason "interrupted" (Pass 8).
- `turn/completed` / `turn/failed` carry a `was_active` guard: a late real end after the interrupt watchdog fired never emits a second turn end (Pass 11).
- `turn/interrupt {threadId, turnId}`. "no active turn to interrupt" is a benign race, treated as already interrupted (Pass 4).
- `error {error:{message, codexErrorInfo}, willRetry, threadId, turnId}`: `willRetry` renders as a transient notice (Pass 4).
- `steered` is not a wire type: steering acceptance is an extra `userMessage` item inside the running turn (Pass 7, vsix). See [Mid-turn messages](#mid-turn-messages-steer-and-queue).
- `userMessage` items carry `clientId` (null unless the client sent `clientUserMessageId`) (Pass 10).

## Items

- `commandExecution`: `{id, command, cwd, status: inProgress|completed|declined, commandActions[{type, command, …}], aggregatedOutput, exitCode, durationMs}`. `commandActions[].command` is the bare command, a nicer title than the `/bin/zsh -lc '…'` wrapper (original probe). The execute `ToolCall` also carries the full command (`command`, clipped to 8 KiB) (Pass 36).
- `commandActions` shapes, present on `item/started` already (Pass 31, codex 0.156.1): `{type: "read", command: "cat notes.txt", name: "notes.txt", path: "<absolute path>"}`, `{type: "listFiles", command: "ls", path: null}`, `{type: "search", command: "rg -n apple .", query: "apple", path: "."}` (path as typed), `{type: "unknown", command}`. `cwd` is a plain absolute path. When every action is read/listFiles/search, the row is a `Read` row (only reads) or a `Search` row (any list or search) titled like the TUI's exploration lines: "Read a.rs, b.rs", "List src" / "List files", `Search "q" in src` / `Search "q"` (a `.` path is dropped), segments joined by " · "; `locations` are the read files, resolved against `cwd`. Any `unknown` action, or none, keeps the `Execute` row. Subagent progress lines use the same titles.
- `item/commandExecution/outputDelta {itemId, delta, threadId, turnId}` is a plain string appended live, capped at `TOOL_OUTPUT_HEAD`; the completed item's `aggregatedOutput` replaces it (Pass 4).
- `fileChange`: `{type:"fileChange", id, status: inProgress|completed|failed|declined, changes:[{path, diff, kind:{type: add|delete|update, move_path?}}]}`. `diff` is full content for add/delete and unified hunks for update; `move_path` is a rename. `item/fileChange/patchUpdated {itemId, changes}` replaces the changes wholesale; the driver re-runs the fileChange upsert on each, so `item_locations` and the Edit card stay current and a later approval names the right files (Pass 2, vsix).
- `mcpToolCall {server, tool, arguments, status, result (MCP CallToolResult), error, durationMs}` (Pass 4). The driver names a chimaera comms call's target in its title (`chimaera.message_agent → s-…`) (Pass 39, codex 0.157.1).
- `webSearch {query, action:{type, url}}` (Pass 4).
- `contextCompaction`: see [Rewind, compaction and fork](#rewind-compaction-and-fork).
- `imageGeneration {id, status, revisedPrompt, result, savedPath?}`: `savedPath` is a filesystem path (preferred; `result` may be a URL, data URL or raw base64). It maps to a tool row whose location opens the image; the completed re-emit upserts by id (Pass 7, vsix).
- `imageView {id, path}` → a Read row whose location opens the image. `dynamicToolCall {namespace?, tool, status, success}` → a generic row. `hookPrompt {fragments[{text, hookRunId}]}` → a "hook: …" Notice (Pass 30, codex 0.153.0).
- `sleep {id, durationMs}` (the model's `clock.sleep`) draws a "sleep: 5m 00s" row (Pass 47, codex 0.162.1).
- `enteredReviewMode` / `exitedReviewMode`, `functionCallOutput` and `plan` items render nothing (Pass 3; Pass 30). No `review/*` RPCs exist (Pass 3, vsix).
- Plans: `turn/plan/updated {plan:[{step, status: pending|inProgress|completed}], explanation}` is the todo list; `item/plan/delta` streams the proposed plan markdown in plan mode (Pass 4).
- `agentMessage {phase: "commentary" | "final_answer" | "partial_answer" | null, delivery: "async" | null, questions: AsyncUserInputQuestion[] | null}`. The schema says providers are inconsistent, so null means unknown. Commentary renders as prose (Pass 31, codex 0.156.1; `partial_answer` Pass 43, codex 0.162.1).
- The `ThreadItem` union at 0.153.0: `agentMessage, collabAgentToolCall, commandExecution, contextCompaction, dynamicToolCall, enteredReviewMode, exitedReviewMode, fileChange, functionCallOutput, hookPrompt, imageGeneration, imageView, mcpToolCall, plan, reasoning, sleep, subAgentActivity, userMessage, webSearch` (Pass 30).

## Reasoning and thinking

- Reasoning deltas stream through `item/reasoning/textDelta` and `item/reasoning/summaryTextDelta`; sections are delimited by `summaryTextDelta`'s `summaryIndex`. The official `summaryPartAdded` handler is a no-op; chimaera inserts a thought paragraph break; `summaryTextDelta` maps to `ThoughtChunk` (Pass 2; Pass 7, vsix; Pass 31).
- Every model in the 0.156.1 bundled catalog declares `"default_reasoning_summary": "none"`, so a thread whose `summary` was never set asks for no summary. Live: 0 of 3 unset turns streamed `summaryTextDelta`; 3 of 3 turns with `turn/start.summary: "auto"` did, and the completed `reasoning` item's `summary` array filled (for example `["**Calculating the result**"]`). One `"detailed"` turn produced none, so emission is model-dependent even when requested. `turn/start.summary` ("for this turn and subsequent turns") is echoed at once as `thread/settings/updated {summary: "auto"}`. The rollout's `turn_context.summary` reads `"auto"` for every turn and is not the value sent to the model (Pass 31, codex 0.156.1).
- A gpt-5.6-sol reasoning item can carry no summary at all (`summary: []`, `item/started` → `item/completed` in 0.6 s, no deltas), even with `summary: "auto"` (Pass 43, codex 0.162.1).
- A reasoning `item/started` on the parent's current turn journals `ThinkingTokens {tokens: 0}` ("thinking, no estimate"), so the status line says "Thinking" while the model thinks; the UI shows no token detail for 0 (Pass 43, codex 0.162.1).
- A summary part is a string or a `{type: "summary_text", text}` object; a leading bold line names a section (`reasoning_section_title`) (Pass 43).

## Token usage and context

- `thread/tokenUsage/updated {threadId, turnId, tokenUsage: {total, last, modelContextWindow}}`; each breakdown carries `inputTokens, cachedInputTokens, cacheWriteInputTokens, outputTokens, reasoningOutputTokens, totalTokens`, with `totalTokens = inputTokens + outputTokens`, so `outputTokens` already includes reasoning (Pass 31, codex 0.156.1).
- Context meter: `tokenUsage.last.totalTokens`, min'd against `modelContextWindow`, not the cumulative total; no baseline subtraction (Pass 4).
- `TurnTokens` for the parent thread only: `total.outputTokens` minus a base taken at the turn's first update (`total − last`, so a resumed thread's history never counts). An update carrying another turn's id is ignored. A new value is journaled only after a move of at least 256 tokens, and once more at turn end if one was held back (Pass 31).

## Approvals and permission modes

- `item/commandExecution/requestApproval {kind: command|writeStdin, threadId, turnId, itemId, command?, cwd?, commandActions?, networkApprovalContext?, proposedExecpolicyAmendment?, proposedNetworkPolicyAmendments?, availableDecisions?, …}` → `{decision}` covers shell, stdin and network approvals (Pass 34 schema, codex 0.157.1). Answer by JSON-RPC id. Any unrecognized decision string is silently treated as a decline (original probe: "approved" declined the command).
- The decision is a string-or-object union: `"accept"` | `"acceptForSession"` | `"decline"` | `{acceptWithExecpolicyAmendment:{execpolicy_amendment}}` | `{applyNetworkPolicyAmendment:{network_policy_amendment}}` (Pass 2, vsix).
- The client composes object decisions from request params: `proposedExecpolicyAmendment` is an array of command tokens (invalid if joining them would contain a newline). A network approval is a regular command approval with `networkApprovalContext.host` + `proposedNetworkPolicyAmendments`: pick the `action:"allow"` entry and send it back verbatim inside `applyNetworkPolicyAmendment.network_policy_amendment` (snake_case key, camelCase amendment). The network card is chosen by the `networkApprovalContext.host` guard inside the command-approval arm only (Pass 4; Pass 34).
- `item/fileChange/requestApproval {itemId, grantRoot?, reason?}` accepts only accept/acceptForSession/decline; its diff resolves by `itemId` against the already-streamed fileChange item (Pass 2; Pass 4).
- UI wording: "Yes" / "Yes, and don't ask again this session" / "Yes, and don't ask again for commands that start with {cmd}" (Pass 2, vsix).
- `item/permissions/requestApproval {threadId, turnId, itemId, environmentId, startedAtMs, cwd, reason?, permissions: {network:{enabled}|null, fileSystem:{read[]|null, write[]|null}|null}}` → `{permissions: GrantedPermissionProfile, scope: "turn"|"session", strictAutoReview?}`, not the `{decision}` union. Allow for turn / for session echo the requested profile; Deny grants `{}` for the turn and is recognized by option id, so deny-with-feedback steers the reason (Pass 30, schema 0.153.0). Live emission is not yet observed.
- Decline has no message field, so a decline with feedback answers `{"decision":"decline"}` and then delivers the reason into the running turn through `turn/steer` (`dispatch_input`). Its ack is final: it is never parked as unread or re-driven, so a Stop right after a deny-with-feedback starts no new turn; a refusal while the turn runs is an Error notice (Pass 9; Pass 38).
- Mode table (UI → wire). `permissions` (a profile id) and `sandboxPolicy` are mutually exclusive on the wire; chimaera sends profiles (Pass 4; Pass 18, codex 0.144.2; Pass 20; Pass 26):

| Mode | `permissions` | `approvalPolicy` | `approvalsReviewer` | collaboration mode |
|---|---|---|---|---|
| read-only | `:read-only` | `on-request` | `user` | cleared |
| auto | `:workspace` | `on-request` | `user` | cleared |
| auto-review (the default at open) | `:workspace` | `on-request` | `auto_review` | cleared |
| full-access | `:danger-full-access` | `never` | `user` | cleared |
| plan | `:workspace` (code: `mode_wire_fields`) | `on-request` | `user` | `{mode:"plan", settings:{model, reasoning_effort, developer_instructions:null}}` |

- Every mode arm explicitly resets the reviewer and the collaboration mode, because `thread/settings/update` is a patch endpoint and would otherwise keep hidden sticky state (Pass 20).
- `approvalPolicy` is `untrusted|on-failure|on-request|never`, or a granular object (`{granular = {sandbox_approval, rules, skill_approval, request_permissions, mcp_elicitations}}`, all five required) (Pass 4; Pass 19). `ApprovalsReviewer` is `user | auto_review | guardian_subagent`; `guardian_subagent` is kept only as accepted upstream vocabulary (Pass 20, codex 0.144.2). The extension's guardian mode maps to `approvalsReviewer guardian_subagent` (Pass 3, vsix).
- Sandbox RPC spelling is camelCase (`workspaceWrite`); config spelling is kebab-case (Pass 3). `permissionProfile/list` → `:read-only | :workspace | :danger-full-access` (Pass 30).
- Full access maps to `approvalPolicy: "never"` (the extension's exact table, kept): codex auto-declines instead of asking, so no `requestApproval` exists. The driver emits a once-per-turn Notice naming the mechanism ("full access never asks — switch to auto mode to be asked") when a declined item lands in full-access mode (2026-07-10).
- Auto review: `item/autoApprovalReview/started|completed {reviewId, targetItemId, action, review:{status: inProgress|approved|denied|timedOut|aborted, riskLevel?, rationale?}}`. The action union is command, execve, applyPatch, networkAccess, mcpToolCall, requestPermissions; the review object is upstream-marked unstable. It maps onto a bounded, upserted tool row; denied is a completed safety verdict, not a failed tool; timeout and abort are failed; unknown actions degrade to a generic bounded row (Pass 7; Pass 20, codex 0.144.2).
- `guardianWarning {threadId, message}` (`GuardianWarningNotification`: no review id to correlate) becomes a visible Notice, except a message that begins `Automatic approval review approved …` at a token boundary: that is a routine duplicate of the structured verdict and is filtered. Unknown wording, near-prefixes, unavailable-review messages and adverse warnings still become notices (Pass 25, codex 0.144.2).
- The guardian runs as a separate thread. Its `thread/settings/updated` (for example effort `low`) belongs to that thread and never replaces the parent's selector (Pass 28, codex 0.144.2).
- Codex's auto-review rows ("auto review · chimaera · message_agent") appear on a pre-approved chimaera MCP call in chat; the call proceeds (Pass 39, codex 0.157.1).

## MCP tool calls and elicitation

- Every codex chat spawn injects `-c mcp_servers.chimaera.url` with a secret-free URL and `-c mcp_servers.chimaera.bearer_token_env_var`; codex reads the env var and sends `Authorization: Bearer <key>`. The env is owner-only, unlike argv in `/proc` (Pass 19 addendum, codex 0.144.2).
- A codex MCP tool call does not raise `item/permissions/requestApproval`. With approvals on, it raises the server request `mcpServer/elicitation/request` (Pass 18, codex 0.144.2):

```json
{"threadId","turnId","serverName":"chimaera","mode":"form",
 "_meta":{"codex_approval_kind":"mcp_tool_call","persist":["session","always"],
          "tool_description":"…","tool_params":{},"tool_params_display":[]},
 "message":"Allow the chimaera MCP server to run tool \"list_terminals\"?",
 "requestedSchema":{"type":"object","properties":{}}}
```

- The reply is the MCP elicitation shape with a required `action`: `{"action":"accept","content":{}}` runs the tool; `{"action":"decline"}` rejects it. An approval-style `{"decision":"accept"}` fails deserialization (`missing field 'action'`) and codex resolves the call as "user rejected MCP tool call". `{"action":"accept","content":{"persist":"session"}}` deserializes and runs, but persistence is unverified, so the driver offers only once/decline (Pass 18).
- The app-server elicits every MCP tool call; nothing config-side gates it. `mcp_servers.<s>.default_tools_approval_mode` (enum `auto | prompt | writes | approve`), `mcp_servers.<s>.tools.<t>.approval_mode`, the granular `mcp_elicitations=false`, and `thread/start {approvalPolicy:"never"}` all parse and are ignored by the app-server (Pass 19, codex 0.144.2). The TUI does honor `approval_mode="approve"` (Pass 35, codex 0.153.0).
- The elicitation params carry no structured tool name, only `serverName` and the pinned message `Allow the {server} MCP server to run tool "{name}"?`. The pre-approval parse is anchored to that exact shape with a `[A-Za-z0-9_-]+` name (a last-quoted-span parse was injectable: a requested name `x" run tool "read_session` would have matched the allow list). A parse failure under a matching consent tracing-warns (Pass 19 addendum).
- `SpawnSpec.mcp_auto_approve {server, tools: Option<Vec>}` is the embedder's standing consent. The driver answers a matching elicitation (`codex_approval_kind == "mcp_tool_call"`, same server, tool parsed from the message) with `{"action":"accept","content":{}}` and surfaces everything else (Pass 19).
- The elicitation arm's `input_preview.params` is capped through `model::cap_preview` (Pass 19 addendum).
- The 0.159.3 schema lists `mcpServer/elicitation/request` modes `form`, `openai/form`, `openaiForm`, `url`; replies are `{action, content: null|JSON, _meta: null|JSON}`. Only `_meta.codex_approval_kind: "mcp_tool_call"` uses the permission path; forms and URLs never inherit its standing consent (2026-10-03). The shared form rules are in [cross-agent.md#mcp-elicitation-forms](cross-agent.md#mcp-elicitation-forms).
- A root `developer_instructions` config string (`-c` injectable) reaches app-server turns (Pass 19). Chimaera now carries its developer note through `thread/inject_items` instead (Pass 41).

## Questions

- `item/tool/requestUserInput` (server request): `{threadId, turnId, itemId, questions:[{id, header, question, isOther?, options?:[{label, description}]}], autoResolutionMs?}`. Answer by rpc id: `{answers:{<questionId>:{answers:[string,…]}}}`; an empty `{answers:{}}` skips. No multiSelect. It renders as a QuestionCard; its parent item never produces a `ToolCall` row (Pass 7, vsix).
- `autoResolutionMs` is honored driver-side: at the deadline the driver answers `{answers:{}}`, withdraws the card (`QuestionResolved`) and drops a visible notice. The relative value is converted once, on receipt, into the driver's monotonic deadline and the normalized absolute `QuestionRequest.expires_at_ms`; the UI countdown is presentation only (Pass 10; Pass 20).
- `serverRequest/resolved {threadId, requestId}`: the server settled its own request (timeout, another client, interrupt). The matching card is withdrawn, `option_id: "cancelled"` (Pass 7).

## Mid-turn messages: steer and queue

The current model: a mid-turn send steers into the running turn and is read at the agent's next step. ⌥↩ (`SendAfterTurn`) queues one for the next turn (Pass 38, codex 0.157.1).

CLI facts:

- `turn/steer {threadId, clientUserMessageId, input, expectedTurnId}` appends input to an in-flight turn. On a turn-id mismatch the live id is parsed from the error text (``expected active turn id `x` but found `y` ``) and the steer is retried once (Pass 3; Pass 4).
- Steering is the default in Codex's own clients: `codex features list` → `steer removed true`; the TUI tip reads "Press {composer.queue} to queue a message when a task is running; otherwise it sends immediately"; the desktop app's `followUpQueueMode: queue|steer` defaults to `steer` (the VS Code extension defaults to `queue`), and its queued rows have "Send now" (Pass 38, codex 0.157.1).
- `turn/steer` answers at once (`{turnId}`); that is acceptance, not reading. The steer's `userMessage` item (`item/started` / `item/completed`, `clientId` = our `clientUserMessageId`) lands at the next step: two steers sent 0.3 s into a `sleep 8` appeared right after its `commandExecution` completed, and the reply came in the same turn (Pass 38).
- An interrupt drops accepted-but-unread steers: `turn/completed {status: interrupted}` arrives with no item and no signal for them, and nothing runs them. The Codex TUI re-submits them itself ("Model interrupted to submit steer instructions"). Re-driving them as a fresh `turn/start` delivered each exactly once. A steer sent right after `turn/started` still waited for the next step. The interrupted `commandExecution` keeps running and completes inside the next turn (Pass 38).
- `turn/steer` with no active turn is refused (Pass 39).
- A `turn/steer` ends the parent's collab `wait` at once: `turn/steer` → `{turnId}` (0.1 s) → `item/completed {collabAgentToolCall, tool: "wait", status: "completed", receiverThreadIds: [], agentsStates: {}}` → the `userMessage` item (0.1–0.2 s after the steer) → the parent's answer → a new `wait` in progress. The child kept running and finished on schedule (Pass 44, codex 0.162.1). One of three runs stalled after the steer (the child emitted one reasoning item and nothing more for 250 s); not reproduced.
- An experimental server-side queue exists: `thread/queue/{add,list,update,delete,reorder,start}`, `thread/queue/changed {threadId}`, and a `codex queue` CLI. Not adopted; queueing stays client-side (Pass 30; Pass 38).
- `instant_interrupt` is a runtime feature flag, not a `turn/steer` field. An app-server launched with `-c features.instant_interrupt=true` reported `experimentalFeature/list` entry `{name:"instant_interrupt", enabled:true, defaultEnabled:false, stage:"underDevelopment"}`; `config/read` also returned the flag. Chimaera's launch setting omits the override or passes true/false; it does not change the queue, the expected-turn precondition or the read acknowledgement (2026-10-03, codex 0.160.0). The billed regression `driver_codex_instant_steering_reads_during_a_response` passed at Pass 43 (codex 0.162.1).

Chimaera's mapping (Pass 38, unless noted):

- A mid-turn send steers at once; in the `turn/start` window it steers once `turn/started` lands. The RPC answer parks it in `unread_steers`; its `userMessage` item resolves it `sent`.
- Every turn end moves unread steers to `deferred_steer_redrives`. `start_next_queued` opens the next turn with all deferred messages merged into one `turn/start` input, in request order; the first message is the turn and the rewind boundary, and each resolves `sent`. A late steer ack after its turn ended re-drives too, unless the item already arrived (`read_before_answer`).
- A steer the running turn refuses without a turn-id mismatch is deferred to the next turn, never dropped: "no active turn to steer" arriving before `turn/completed`, and "cannot steer a compact/review turn" (`activeTurnNotSteerable`). So is a second refusal after the one turn-id retry.
- Inference, not observed: codex also drops unread steers at a normal completion (from its loop and the interrupt probe). If a later codex carried leftover input into its next turn, re-driving would deliver it twice. Re-probe on a version bump.
- `SendAfterTurn` → the next-run FIFO: each real turn end (completed, interrupted or failed) promotes exactly the oldest entry into a fresh `turn/start`; later entries stay queued. A turn end with steer RPCs still unresolved gates FIFO promotion until the last acknowledgement; failed steers re-drive first, in click order (Pass 21).
- The queued follow-up's `Checkpoint` is emitted at promotion, never at queue time. Rewind truncation replaces the early queued echo with a `Cancelled` tombstone at the same seq and cuts at the late checkpoint (Pass 21).
- Send now → `turn/interrupt`; an after-turn entry joins the re-driven batch.
- ✕ on a still-queued entry removes it (`Cancelled`). ✕ on a steered message is a Notice: it cannot be withdrawn. An id whose steer RPC is in flight gets the "on its way" Notice. An already-resolved id gets the replay-stable tombstone `Cancelled` (Pass 14; Pass 38).
- Stop never discards the FIFO. The interrupt watchdog and teardown resolve held entries `dropped`, because a re-driven `turn/start` would strand against a wedged process (Pass 14; Pass 21).
- `SteerQueued{id}` (`{type:"steer_queued", id}`) is still accepted from old clients; a click during the `turn/start`→`turn/started` window (`turn_pending`) records the intent until `expectedTurnId` is known (Pass 21; Pass 38).
- Idle-flush rescue (`IDLE_FLUSH_GRACE_TICKS`, 1.5 s): a turn end that fires while a `turn/start` is still in flight leaves waiting input with no turn to promote it. When the driver is idle with a stranded queue past the grace, it opens the oldest entry as a fresh turn and delivers it, rather than declaring it sent unseen (Pass 12; code: `idle_flush`).
- The harness `tick` also runs `expire_questions` (Pass 11).
- `SendIfRunning` (agent-to-agent messages) steers the running turn under its own key (`agent_steers`). A refused steer, or one the turn never read, becomes `UserMessageUpdate{Dropped}` and is never re-driven into a `turn/start`; the user's Send now on such a message still delivers it (Pass 39, codex 0.157.1).

## Multi-agent (collab)

- Codex uses collab out of the box when asked; the model's tools are SpawnAgent/SendInput/ResumeAgent/CloseAgent (binary-mined). The wire surfaces them as parent-thread items plus whole extra threads (Pass 16, codex 0.144.2).
- **Two multi-agent runtimes, two wire shapes.** The model's catalog metadata (`multi_agent_version`, `MultiAgentVersion = "disabled" | "v1" | "v2"`) picks the runtime, and it wins over `features.multi_agent_v2` (`stable`, default false): `-c features.multi_agent_v2=false` still gave gpt-5.6-sol v2. In the account's catalog gpt-6.1-sol, gpt-6-astra, gpt-6-sol, gpt-6-luna, gpt-5.6-sol and gpt-5.6-terra are v2; gpt-5.6-luna, gpt-reserve and codex-auto-review are v1; a model without metadata (any custom `model_provider`, local or OSS models: "Model metadata for `…` not found. Defaulting to fallback metadata") is v1, and `features.multi_agent_v2=true` makes it v2 (Pass 51, codex 0.158.0, 0.162.1, 0.164.0).
- v2 offers the model a `collaboration` namespace (`spawn_agent`, `wait_agent`, `send_message`, `followup_task`, `interrupt_agent`, `list_agents`) and reports spawn/input/close/finish as `subAgentActivity` markers; only `wait` is a `collabAgentToolCall` (below). v1 offers a `multi_agent_v1` namespace (`spawn_agent {message, items?, fork_context?, agent_type?, model?, …}`, `send_input {target, message|items, interrupt?}`, `resume_agent {id}`, `wait_agent {targets, timeout_ms?}`, `close_agent {target}`), sends **no `subAgentActivity` at all**, and reports every call as a `collabAgentToolCall` (Pass 51).
- `subAgentActivity {type, id, kind, agentThreadId, agentPath, model?, reasoningEffort?}` on the parent thread (v2). `agentPath` is a namespace path whose last segment is the model's name for the agent ("/root/agent_a"). `kind` is `started | interacted | interrupted | completed` (0.156.1 schema). `started` and `completed` arrive as an `item/started` + `item/completed` pair at 0.156.1; the driver acts on `item/completed` only (Pass 16; Pass 31). `model` and `reasoningEffort` are new at 0.162.1 ("Resolved model at sub-agent creation; absent from older records and other activities"; live: `gpt-5.6-sol` / `xhigh` on `started`, null on the others) (Pass 43).
- Observed order at spawn: the parent's `subAgentActivity` marker, then the child's `turn/started`. No `thread/started` arrives for a child; its first frame is `thread/status/changed {idle}`, between the spawn marker's `item/started` and `item/completed` (Pass 16; Pass 31; Pass 42).
- At a child's finish (0.162.1): the parent's `subAgentActivity {completed}` `item/started` (t+0 ms), the child's `turn/completed` (+1 ms), the marker's `item/completed` (+5 ms); the item id is `subagent-completed-<uuid>`, not a collab call id (Pass 31; Pass 43).
- `collabAgentToolCall {type, id, tool, status (inProgress|completed|failed|interrupted), senderThreadId, receiverThreadIds[], prompt, model, reasoningEffort, agentsStates{[thread]: {status, message}}}`, as a started + completed pair. On v2 only `tool:"wait"` surfaces, with `receiverThreadIds` and `agentsStates` empty (Pass 16; Pass 31; Pass 44). `CollabAgentTool` is `spawnAgent | sendInput | resumeAgent | wait | closeAgent | sendMessage | followupTask | interruptAgent | listAgents`; `CollabAgentStatus` is `pendingInit | running | interrupted | completed | errored | shutdown | notFound`; both unchanged through 0.164.0 (Pass 31; Pass 51).
- v1 shapes (Pass 51; identical on 0.158.0, 0.162.1 and 0.164.0, hermetic and live with gpt-5.6-luna). The tool names are camelCase on the item (`wait_agent` → `wait`, `close_agent` → `closeAgent`); the item id is the call id (`call_…`, or `exec-<uuid>` from luna). `spawnAgent` `item/started` has `receiverThreadIds: []`, `model: ""`, `prompt` = the task; its `item/completed` names the child thread in `receiverThreadIds`, the resolved `model` ("gpt-5.6-luna") and `reasoningEffort`, and `agentsStates {<child>: {status: "pendingInit", message: null}}`. The child's `thread/status/changed {idle}` and `turn/started` follow the completed item (1–2 ms). `wait` names its targets in `receiverThreadIds`; its completed `agentsStates` carries each verdict (`{status: "completed", message: "42"}`), and live it landed 1 ms BEFORE the child's own `turn/completed`. `closeAgent` names its target; the child's status then goes `notLoaded`. No item carries an `agentPath`; the child's name is its `agentNickname` ("Planck", "Dalton", "Kepler"), which is also what the parent model reads in the spawn output (`{"agent_id": …, "nickname": "Planck"}`).
- `send_message` to an agent that already answered only queues the message for its next turn: no child turn starts and the child thread sends nothing. It still surfaces as `subAgentActivity {kind: "interacted"}`, as do `followup_task` and a message to a working agent (Pass 43, codex 0.162.1).
- No child `thread/started` reaches the parent connection, so `agentNickname` / `agentRole` are not available from the stream; on v2 row labels stay the `agentPath` leaf, and the nickname comes only from `thread/read` (Pass 31; Pass 42; v1 in Pass 51).
- The rollouts name the collab calls `spawn_agent`, `wait_agent`, `followup_task`, `send_message` (Pass 43). The binary also names activity variants `subAgentThreadSpawn` / `subAgentActivity` / `subAgentCompact` / `subAgentOther`; unseen kinds are folded onto the row verbatim (Pass 15; Pass 16).
- A delegated agent outlives the parent turn: the parent `turn/completed` can arrive first, and the child keeps emitting its own frames until its own `turn/completed` (Pass 27, codex 0.144.2).
- Delegation config: `multiAgentMode` is `{custom: string} | explicitRequestOnly | proactive` at 0.153.0 (`none` is gone; camelCase on the wire). At 0.156.1 `ThreadSettingsUpdateParams.multiAgentMode` is `@deprecated Ignored. Use effort: "ultra" for proactive multi-agent behavior`. Not exposed in chimaera (Pass 16; Pass 30; Pass 31).
- SubagentStart/SubagentStop hook events are codex's hook system, not this wire; not consumed (Pass 16).

Chimaera's mapping (claude-symmetric):

- The subagent surface is an `Agent: {name}` tool row (`ToolKind::Agent`, row id `agent:{agentThreadId}`, name = the last `agentPath` segment) that the AgentsTray derives from. Foreign-thread frames fold into its progress line ("{last} · N tools · M tokens"; tokens from the agent thread's `tokenUsage`, throttled to ≥ 256-token moves) (Pass 16).
- Status words on a row use the status line's vocabulary ("Working" at a turn start, "Thinking", "Writing", "Delegating") and the newest section title of a finished reasoning summary, held until a tool or reply replaces it. Counts use `model::fmt_tokens` (Pass 43).
- A stint opens at spawn (`started`) or, for new work, at the child's own `turn/started`. The child's `turn/completed` closes it ("answered"; a deliberate stop closes quietly); `interrupted` closes it ("closed"). "interacted" never opens a stint: a working agent's row gets a "Follow-up input" note (Pass 43). A follow-up to a closed agent opens a new row `agent:{thread}#N`, because the UI's tool-status guard is monotonic (Pass 16).
- `completed` is a no-op for a closed row, closes a row only when the agent's own turn is not known to be running, and never opens one. Unmined kinds open a row only for an unknown agent and otherwise just note the word (Pass 31).
- A marker for a thread the driver never saw spawn (a thread resumed after a daemon restart, or one the cap evicted) parks the agent closed without a row; its own `turn/started` then opens the first stint under `agent:{thread}@<ms>` (Pass 43).
- v1 (Pass 51): a completed `spawnAgent` item opens the row for each `receiverThreadIds` entry (its started twin, which names no thread, draws nothing; there is no separate "Spawn agent" row), titled by the prompt's first line until the child's `thread/read` names its `agentNickname`, which re-emits the open row as `Agent: {nickname}` (a closed row is never re-emitted: a ToolCall re-emit is an in-progress upsert). The item's `model` reaches `SubagentInfo` at once. A spawn that failed or names no thread keeps a failed "Spawn agent: …" row; an interrupted spawn that names its thread still opens the agent row, and an interrupted call closes and notes nothing on its agents' rows but still parks an unseen receiver. A receiver the spawn's own `agentsStates` reports `notFound` or `shutdown` opens no row. A completed `sendInput` / `resumeAgent` (and `sendMessage` / `followupTask`, should they ever surface as items) notes "Follow-up input" on a working agent, like v2's "interacted"; an unseen receiver is parked, as above, and read for its nickname. `closeAgent` closes an open row "closed" (`stopped`), like v2's "interrupted". A completed call's `agentsStates` closes an open row only when no turn of the agent's is known to be running (`completed` → "answered", whose `message` stands in as the answer when the child's frames never arrived; `errored` → failed; `interrupted`, `shutdown`, `notFound` → stopped), the rule of v2's `completed` marker. `wait` keeps `COLLAB_WAIT_TITLE`, so the main-thread fold still classes it as a subagent wait.
- Each stint's open→closed edge journals one `SubagentFinished {id: "agent:{thread}[#N]", label: <agentPath leaf, or the v1 nickname>, status, result, stats}`. `status` is `completed`, `stopped` (the `interrupted` marker, or a child turn ending `interrupted`) or `failed`. `result` is the stint's last child `agentMessage` whose `phase` is not `commentary` (a `partial_answer` is a candidate; the latest wins), trimmed and capped at `SUBAGENT_RESULT_MAX` (Pass 31; Pass 43).
- Collab rows carry additive `cross_turn:true`. The registry is process-scoped, not parent-turn-scoped; parent completion or abort is not a child close. The manager folds live cross-turn agent ids into `background_running` (Pass 27). Driver teardown fails open rows and journals no finish line (Pass 16; Pass 31).
- Over the 32-row cap (`COLLAB_AGENTS_CAP`) closed rows are evicted first; when every slot is live the newest agents are not tracked and a once-per-turn Notice says so (Pass 16).
- `wait` renders as an ordinary tool row titled `COLLAB_WAIT_TITLE` ("waiting for subagents"), upserted on completed. Other collab tools get readable titles that name `receiverThreadIds` by tracked agents' names (an untracked id shows as `agent …<last 6>`; at most three names, then "+N more"): "Message → agent_a: …", "Follow-up → agent_a", "Interrupt agent_a", "List agents", "Spawn agent: …", "Input → …", "Resume …", "Close …"; unknown tools keep "collab {tool}" (Pass 16; Pass 31).
- A subagent's `fileChange` items record `item_locations`, so its approval card names the files; its `error` notifications fold into the progress line. Nested delegation shows as that agent's "delegating" progress, with no nested rows (Pass 16).
- No stop affordance: the collab tools are the model's, and no client→server RPC to stop a single subagent is known (`turn/interrupt` on the child's turn is unprobed) (Pass 16).

## Reading a subagent's thread

- `thread/read {threadId: <child>, includeTurns: false}` answers already at the spawn marker (live: `status: {type: "idle"}`, `turns: []`) with the child's `model` (the parent's model in every probe), `reasoningEffort`, `agentNickname` (random, "Dewey"), `agentRole` (null), `parentThreadId`, `threadSource: "subagent"`, `source: {subAgent: {thread_spawn: {parent_thread_id, depth, agent_path, agent_nickname, agent_role}}}`, `canAcceptDirectInput: false`, `historyMode: "paginated"` and the rollout `path`. It also reads threads the server has not loaded (`status: {type: "notLoaded"}`) (Pass 42, codex 0.158.0).
- `SubagentInfo` with the model comes from the spawn marker's `model` at row open (Pass 43), then from one `thread/read` per child at row open, retried once at the child's `turn/started` (Pass 42).
- `thread/read {includeTurns: true}` returns `thread.turns[{id, status, items, itemsView: "full", startedAt, completedAt, durationMs, error}]` in the live `ThreadItem` shapes. A read of a running turn returns only its completed items, so successive reads extend each other. A v2 child's prompt is not among its items; a v1 child's turn opens with its prompt as a `userMessage` (the v2 child is a fork of the parent, `forkedFromId` set; the v1 child is not) (Pass 42; Pass 51). A failed turn reads back `{status: "failed", error: {…}}`. `DriverQuery::SubagentTranscript` → `thread_to_events` replays the turns through an offline mapper, leaving the newest turn open when live (Pass 42).
- `includeTurns: true` is preceded by `deprecationNotice {summary: "Full-history hydration is deprecated for paginated threads; …page with thread/turns/list and thread/items/list."}`, suppressed while a read is pending. A history over the 8 MiB ndjson line cap cannot be read whole; paging is the follow-up. An invalid id answers `-32600 "invalid thread id: …"` (Pass 42).

## Rewind, compaction and fork

- `thread/revert {threadId, beforeTurnId}` replaces a paginated thread's durable history with the prefix before one turn; that turn and every later turn are excluded. The response's `thread.turns` is always empty, with `turnsBackwardsCursor` / `itemsBackwardsCursor`; a `thread/reverted {threadId}` notification follows (Pass 30, schema 0.153.0).
- `thread/rollback {threadId, numTurns}` is deprecated and refused on paginated threads (`{"code":-32600,"message":"paginated threads do not support thread/rollback"}`, 0.153.0); it is gone from the schema since 0.156.1 (Pass 30; Pass 33). On older binaries it drops the last `numTurns` turns in place, works right after `thread/resume`, and silently clamps an overcount, so the count must be exact (Pass 10, codex 0.142.5).
- Chimaera's rewind: codex `Checkpoint` events anchor turn-opening sends only (rollback cannot cut mid-turn). The server truncates the journal at the anchor, counts the dropped `TurnStarted` events and records the first dropped turn's native id (`DroppedTurns.first_turn_id` → `SpawnSpec.revert_before_turn`). The handshake sends `thread/revert`; any failure but a transport error still tries the count-based `thread/rollback`, and the revert's error is reported if both fail (Pass 10; Pass 30). Turns run outside the journal (TUI-interleaved through the view toggle) are invisible to the count. A rewind cut before a portable branch marker is refused (Pass 30).
- `thread/compact/start {threadId}` → `{}`. Compaction runs as its own turn: `thread/status/changed active` → `turn/started` → `item/started` / `item/completed` of a `contextCompaction` item → `turn/completed`. No `thread/compacted` notification fires (0.142.5); the item pair maps to the shared `ContextCompaction` lifecycle, and the deprecated notification is a deduped completion fallback (Pass 10, codex 0.142.5).
- `thread/fork {threadId, lastTurnId?, cwd?, model?, modelProvider?, approvalPolicy?, sandbox?, config?, baseInstructions?, developerInstructions?, personality?, ephemeral?}`. `lastTurnId` is inclusive and must name a completed turn; the response carries a distinct `result.thread.id`. Chimaera sends the selected model, cwd and `ephemeral:false`, then treats the thread like a normal opened thread. A final assistant message becomes native-forkable only after its parent `turn/completed` supplies the turn id (Pass 24, codex 0.144.2). The extension's own uses: edit-last-message = rollback 1 on the live thread + re-send; fork-from-turn = `thread/fork` (thread/start-shaped params, `ephemeral` flag) then rollback `total - target - 1` on the fork (Pass 10, vsix).

## Models, effort and settings

## Usage limits

Recorded at codex 0.162.1 (Pass 46).

- `account/read` returns only `{account: {type, email, planType}, requiresOpenaiAuth, workspaceRouting}`; it no longer carries limits.
- `account/rateLimits/read {supportsLunaReserve?, excludeResetCreditDetails?}` → `{ordinaryUsageAllowed: bool | null, rateLimits: RateLimitSnapshot, rateLimitsByLimitId: {[limitId]: RateLimitSnapshot} | null, rateLimitResetCredits: {availableCount, credits: [...] | null} | null, accountId, rateLimitUpsell}`. `rateLimits` is the "backward-compatible single-bucket view". `ordinaryUsageAllowed` is the backend's verdict ("clients must not infer recovery from percentages or reset times"). `excludeResetCreditDetails: true` skips the reset-credit lookup "for background usage polls"; 0.162.1 ignores an unknown param here.
- `RateLimitSnapshot` = `{limitId, limitName, normalModelSlug, primary: RateLimitWindow | null, secondary: RateLimitWindow | null, credits: {hasCredits, unlimited, balance} | null, individualLimit, spendControlReached, planType, rateLimitReachedType: "rate_limit_reached" | "workspace_owner_credits_depleted" | … | null}`. `RateLimitWindow` = `{usedPercent (0-100), windowDurationMins | null, resetsAt (epoch s) | null}`.
- Live, a Pro account: `limitId: "codex"`, one window `{usedPercent, windowDurationMins: 10080, resetsAt}` as `primary`, `secondary: null`, `rateLimitsByLimitId` holding the same bucket.
- `account/rateLimits/updated {rateLimits: RateLimitSnapshot}` is a "sparse rolling rate-limit update": clients merge available values into the last read, and a null field "does not clear a previously observed value". Codex sends it during every turn, before `turn/completed`.
- Mapping: `/usage` (`GetUsage`) sends `account/rateLimits/read {excludeResetCreditDetails: true}`. The chip follows the rolling update. There is no read at turn end: one still in flight held the app-server open long enough that an immediate resume was refused with `thread … already has an active writer` (reproduced twice). A read replaces the held bucket; an update merges non-null windows and a set `rateLimitReachedType`; an update for another `limitId` is ignored. The chip (`RateLimit`) is the fullest window, journaled only on change, and `windows` carries primary/secondary. `limit_reached` comes from `rateLimitReachedType`, `ordinaryUsageAllowed: false`, or a window at 100%. Labels use Claude's words: ≤ 6 h "session limit", 7 d "weekly limit", else "Nh" / "Nd limit", "usage limit" without a duration. A refused read (an API-key login) leaves the chip empty and answers `/usage` with an empty report. Multi-bucket limits and reset credits are not shown.
- `account/rateLimits/read` also carries `rateLimitsByLimitId` and `rateLimitResetCredits` at 0.153.0 (Pass 30).

## Goals

Recorded at codex 0.162.1 (Pass 47).

- `thread/goal/get {threadId}` → `{goal: null | {threadId, objective, status, tokenBudget, tokensUsed, timeUsedSeconds, createdAt (epoch s), updatedAt}}`. `thread/goal/set {threadId, origin: "user", objective?, status?, tokenBudget?}` → `{goal}` + `thread/goal/updated {threadId, turnId|null, goal}`. Status: `active | paused | blocked | usageLimited | budgetLimited | complete`.
- An active goal starts a turn at once, and the server starts continuation turns itself, back to back (no userMessage item), until the model marks it `complete`. `thread/goal/updated` arrives after every tool call with growing `tokensUsed` / `timeUsedSeconds`.
- Setting a new objective on a `complete` goal keeps `status: complete`, the old tokens and `createdAt`: clear first for a fresh goal.
- `{status: "paused"}` stops continuations; `{status: "active"}` resumes and starts a turn immediately. `thread/goal/clear` → `{cleared: true}` + `thread/goal/cleared {threadId}`; a running turn finishes and none follows. `thread/goal/cleared` also follows a rollback (Pass 10).
- `turn/interrupt` does not pause a goal (the TUI also sends `{status: "paused"}` on Stop). TUI words: "Usage: /goal [<objective>|clear|edit|pause|resume]", "Goal paused (/goal resume)", "Goal stalled", "Goal hit usage limit", "Goal budget reached", "Goal achieved".
- No scheduled work exists on this wire beyond goals: none of the 244 methods and notifications in the generated schema creates, lists or runs a schedule. Codex automations belong to the Codex app and cloud. Plugins may declare `scheduledTasks` (`{key, name, prompt, schedule: hourly {intervalHours, days?} | daily {time} | weekdays {time} | weekly …}`), visible only in `plugin/read`; the app-server never runs them.
- Mapping: `thread/goal/updated|cleared` for its own thread map to `Goal` (status verbatim; tokens and time throttled to one event per 10 s, flushed at turn end; the move into `complete` ends it `achieved` once). The goal is read once the thread opens. A server-started turn while the goal is active carries `TurnCause goal`. `SetGoal` clears an existing goal first. The user's Stop pauses an active goal before interrupting; a Send-now interrupt does not. Capabilities `set_goal`, `pause_goal`, `resume_goal`, `clear_goal`.

## Remote Control

- `remoteControl/status/changed {status: disabled|connecting|connected|errored, serverName (hostname), installationId, environmentId}` arrives right after `initialize`. Remote Control is a property of the app-server process: a per-session stdio app-server reports `disabled`, and the client protocol has no enable RPC (the 0.153.0 `ClientRequest` union has no `remoteControl/*`; `RemoteControlEnableParams {ephemeral?}` exists only for the daemon's own control socket). The switch is `codex remote-control start` / `codex app-server daemon enable-remote-control` + `codex remote-control pair` (Pass 30, codex 0.153.0).
- Mapping: status relay only. The first non-`disabled` status starts journaling `RemoteControl` events; unknown words become a Notice; repeats dedupe; teardown journals Off. `SetRemoteControl` answers with a Notice naming the commands above. Full Codex Remote Control would mean attaching to the shared daemon (`codex app-server proxy` / `--listen unix://`), a lifecycle change not taken (Pass 30).
