# ACP v1: Grok Build, Google Antigravity and Cursor CLI

The current contract of the shared ACP adapter (`src/acp.rs`). The pins are `TESTED_GROK_VERSION`, `TESTED_AGY_VERSION` (the standalone server), `TESTED_AGY_CLI_VERSION` (`agy acp`) and `TESTED_CURSOR_VERSION`; the live gate is `just chat-smoke-acp`. Each fact names the pass or date and the agent version where it was recorded, for example "(Pass 45, grok 1.0.46)". A fact tagged "(2026-10-01)" alone was recorded at Grok Build 1.0.46 and agy-acp 1.2.1, the 2026-10-01 live probe. The dated record is [passes.md](passes.md); the shared rules are in [cross-agent.md](cross-agent.md).

## Handshake and authentication

- All three speak JSON-RPC over newline-delimited stdio and negotiate `protocolVersion: 1` (2026-10-01; 2026-10-14).
- Grok and Antigravity advertise `loadSession`, `sessionCapabilities.resume`, HTTP MCP servers, and stream `session/update` (2026-10-01).
- Cursor's `initialize` → `agentCapabilities` = `loadSession: true`, `mcpCapabilities {http, sse}`, `promptCapabilities {image: true, audio: false, embeddedContext: false}`, `sessionCapabilities {list: {}}`. There is no `resume`, so a reopened chat uses `session/load`; its history replay arrives during the handshake and is discarded there (Chimaera's journal owns the transcript). One auth method: `cursor_login` ("Authenticate using existing Cursor login credentials. Run 'agent login' first if not logged in.") (2026-10-14).
- Grok advertises `grok.com` auth but accepts `cached_token` with `_meta.headless: true` for an existing login. Google's `oauth-personal` reuses the existing personal login; other Google methods are advertised but not selected by the adapter. Auth is never copied into Chimaera state (2026-10-01).
- Cursor's `authenticate {methodId: "cursor_login"}` while signed out does not fail fast: it starts Cursor's browser login. With `NO_OPEN_BROWSER=1` it answers `-32602 Invalid params` with `data.message` "Failed to open browser for login. Please visit: https://cursor.com/loginDeepControl?challenge=…", a one-time challenge owned by that process. The adapter's `sign_in` hint replaces the error: "Cursor CLI is not signed in on this host. Run `cursor-agent login` in a terminal, then start the chat again." `session/new` without authentication → `-32000 Authentication required`. A daemon must never open that login itself (2026-10-14).
- The adapter reports `startup_progress` for authentication and session opening before `Init` (2026-10-01).
- A long-lived `grok agent stdio` process keeps the plan tier it authenticated with: after an account upgrade its turns kept failing `subscription:free-usage-exhausted` until the chat's process restarted (2026-10-05, grok 1.0.46).

## Sessions, catalogs and controls

- `session/new {cwd, mcpServers}` returns the native id and the account model catalog. Grok's catalog after authentication included `grok-4.7`; Google's included Gemini 3.8 Flash effort-specific model ids. Do not hardcode these lists (2026-10-01).
- `configOptions` supplies select controls by category (`model`, `mode`, `thought_level`); `session/set_config_option` returns the authoritative current values. `config_option_update` can replace controls; absence removes an effort control (2026-10-01).
- Image input follows the negotiated capability: Grok advertised false, Google and Cursor true. Buttons and attachment admission follow it (2026-10-01; 2026-10-14). Grok 1.0.70 advertises `promptCapabilities.image: true`, so Grok chats now offer images; its model rejects images under 512 px (a 16 px PNG was "below the 512-pixel minimum", a 600 px one was read) (Pass 59).
- agy-acp 1.4.5 reshaped `configOptions`: the model option lists families (`gemini-4-argon`, `gemini-3.8-flash`) and a separate `thinking_level` option (category `thought_level`: low/medium/high) carries the effort, while the legacy `models.availableModels` still lists effort-suffixed ids. The adapter is config-first, so the controls follow; A model id the agent does not offer, but whose `-<level>` suffix splits into an offered model and an offered thinking level, is sent as both values, so a pick remembered from 1.2.1 (`gemini-3.8-flash-high`) restores quietly. agy runs two `set_config_option`s at once, and a model change resets the level: written back to back, `model` then `thinking_level low` answered the level first, still `high`; answered one at a time, both apply. So a thinking-level change waits while a model change is unanswered and goes out once that answer lands (Pass 61). `authenticate` and `session/new` return `_meta.antigravity.tier {id, name, upgradeUri}`; `agentCapabilities._meta.antigravity {systemPrompt: {append: true}, tier: true}` advertises `session/new` `_meta.antigravity.systemPrompt.append` (live: extra system text reached the model); a `/usage` command is new (Pass 59).
- Grok 1.0.70 honours `session/new` `_meta.rules` as extra system-prompt text (live), sends `session_info_update {title}` (Cursor too), reports per-turn usage in `PromptResponse._meta.usage {inputTokens, outputTokens, cachedReadTokens, reasoningTokens, modelCalls, costUsdTicks, modelUsage}` and `_x.ai/session_notification {turn_completed, usage, elapsed_ms}`, and streams `_x.ai/queue/changed {entries, runningPromptId}`; `--plugin-dir` is now accepted by `grok agent`. None is adopted (Pass 59).
- Cursor's bundle (2026.10.14 and 2026.10.22) has two opt-in client capabilities: `clientCapabilities.subagents` (or `_meta.subagents`) turns on `subagent_spawned {subagentSessionId, name, task, capabilities, _meta.cursor {toolCallId, agentId, model}}`, `subagent_state_update {subagentSessionId, state}` and `session/update` frames addressed to the child; `_meta.parameterizedModelPicker: true` replaces the 47 variant model strings with plain ids, per-model parameters appearing once a model is chosen. Bundle shapes only, no live turn; not adopted (Pass 59).
- `available_commands_update {availableCommands: [{name, description}]}` replaces the composer's command list. The adapter bounds it with the shared `cap_slash_catalog` (256 rows, 96 KiB of serialized rows; names over 128 bytes or with a control character are dropped whole, duplicates fold). Until Pass 63 it read the list through the 64-row picker bound (`MAX_CHOICES`), which cut Cursor 2026.10.22's ~78 commands (seen in Pass 59). Gate for the change: a hermetic test with 78 and 5000 commands, and `antigravity_stream_replay_and_resume` live on agy-acp 1.4.5; the Grok and Cursor live cases were not run (Pass 63).
- ACP stays catalog-only: no custom model input. `chat.newSessionModel=agent` omits remembered model and effort through the shared server path; explicit and saved conversation settings still take precedence (2026-10-04, agy-acp 1.2.1 and grok 1.0.46).
- The modes and models a Cursor session offers come only from its own `session/new` result and `configOptions`; nothing is manufactured (`cursor_offers_only_what_its_session_advertises`). Cursor's documentation names modes `agent`, `plan`, `ask` (pending a signed-in run) (2026-10-14).
- `session/resume` restores provider history without replaying it; Chimaera's journal restores the visible transcript. `session/load` is the compatibility fallback (2026-10-01).

## Grok modes

Recorded at grok 1.0.46 (probed 2026-10-04/05, with model turns on the second day).

- Grok advertises no modes: `session/new` has no `modes` and no `mode` config option (its `configOptions` are `model` and `reasoning_effort`).
- Always-approve: a `session/prompt` whose text is `/always-approve on` (or `off`) runs inside Grok and returns `end_turn` with `_meta.totalTokens: 0` and no message chunks. Measured with one shell command: default asked (`session/request_permission`), after `on` it ran unasked, after `off` it asked again. Nothing reads the state back mid-session (`_x.ai/sessions/changed` kept `yolo: false`), so the zero-token answer is the only confirmation. A slash Grok does not know (`/auto on` on an account without Auto-review) goes to the model and is billed. The adapter offers Normal / Always-approve only while `available_commands_update` lists `always-approve`, sends the switch between turns (it occupies the session like a turn: sends queue behind it, and it waits for a running turn), and treats any answer that billed tokens as "not switched". A handshake restore is not a pick (`restoring`). `_meta.yoloMode: true` on `session/new` starts a session in it (`yolo: true` is reported then).
- Plan: `session/set_mode` answers `{}` for any `modeId`; only `plan` and `default` do anything, each confirmed by a `current_mode_update`. In plan mode Grok writes `plan.md` in its session directory, calls `exit_plan_mode`, and sends the client a JSON-RPC request `_x.ai/exit_plan_mode {sessionId, toolCallId, planContent}`, then often `_x.ai/ask_user_question`. The reply shape for the approval is unknown: an error cancels the turn, and `{}` or every guessed field (`approved`, `approve`, `accepted`, `outcome`, `decision`, `action`, …) reads as "The user wants to revise the plan". The adapter does not offer Plan until that shape is captured from the TUI.
- Auto-review is gated per account (`_x.ai/settings/update` `auto_permission_mode_enabled`, null on the probed account; `/auto` is then absent from the command list).

## Turns, queue and cancellation

- A `session/prompt` response ends the turn (`end_turn` or `cancelled`) (2026-10-01).
- A queued prompt starts after the preceding prompt response, not after the cancel notification is written (2026-10-01).
- Cancellation resolves open permission requests as cancelled before sending `session/cancel` (2026-10-01).
- ACP v1 has no mid-turn input: `session/prompt` is one at a time. A message to a busy ACP chat waits for the turn to end and then meets the wake policy (Pass 44).
- `agy acp` (1.5.12) takes a `session/prompt` sent while a turn runs into that turn, as Google's docs say. Probed: a second prompt while a shell command ran made the running prompt answer `end_turn` at once, and the work went on under the new request, whose answer ended the turn and used the new text. While a permission or a question is open it refuses at once: `-32603 "Can't add this prompt to session …: the running prompt is waiting for a permission or question answer; answer it or send session/cancel, then send this prompt again"`. The adapter (`AcpAdapter::steers`, `agy acp` only) sends a Send mid-turn straight away when no approval, question or form is open, nothing waits in the queue and no other steer is in flight; the bubble is `queued` (not `after_turn`) until the running prompt's `end_turn`, then `sent`, and the turn ends with the steer's answer. A refusal or a cancel puts the message first in the queue for the turn's end, joined in one prompt with whatever waits behind it in the order sent (so Send now during an unsettled steer delivers both at once); `SendIfRunning` steers the same way (the adapter then lists `send_if_running`) and a refusal settles it `dropped`. `SendAfterTurn` and Send now keep the queue path; the standalone server never steers (Pass 62).
- Send now cancels the turn and sends every waiting message as ONE `session/prompt`, their blocks in the order sent, whichever bubble was pressed; each resolves `sent` with it. ✕ on one of that batch before it goes removes only its part. Before, the pressed message jumped the queue alone and the rest went one turn each (Pass 60).
- No native fork is advertised. A conversation copy is held in the mapper until the first real user message and prepended to that prompt; opening a fork must not synthesize a turn. The handoff stays pending until the provider emits response content or tool activity, or completes the first prompt; then the driver journals `ForkContextConsumed`. A JSON-RPC rejection before acceptance keeps the copy for retry. An undelivered copy is recovered from its journal marker after a restart or reopen (2026-10-01).
- `agy acp`'s finished shell call carries `content` text and `rawOutput {output, exit_code}`, both opening with "Created At: …\nCompleted At: …\nCommand exited with code N.\n\nCommand output:\n" (the two time lines absent when the command went async), the output keeping the terminal's `\r\n`. The adapter cuts only that exact preamble and turns `\r\n` into `\n` for both Antigravity servers. A completed agy update whose `exit_code` (or `exitCode`) is non-zero is `failed`, as codex's rows are (Pass 62).
- A finished shell call's output: Grok sends it as `content` text. agy-acp 1.4.5 and Cursor 2026.10.22 send no `content`, only `rawOutput`: agy `{commandLine, workingDir, exitCode, exit_code, combinedOutput, formatted_output}`, Cursor `{exitCode, stdout, stderr}`. A completed or failed update with no `content` draws `combinedOutput`, else `stdout` then `stderr`, capped like `content` (2026-11-04).

## Permissions

- Permission requests are agent-initiated JSON-RPC requests (`session/request_permission`). Replies preserve the original numeric or string id and choose only an offered `optionId` (2026-10-01).
- ACP permission replies contain only the selected option id; there is no feedback field. Grok's TUI-derived reject label mentions feedback, but chimaera labels that action "Deny" and shows no feedback or rule-destination controls (2026-10-01).
- Permission requests stay native; no consent is inferred from a tool's display title (2026-10-01).
- Option sets seen (Pass 45): Antigravity `allow_always` / `allow` (`allow_once`) / `deny` (`reject_once`); Grok `always-allow` / `allow-once` / `reject-once`; Cursor `allow-once` / `allow-always` / `reject-once` (Cursor's docs list the same three).
- Grok 1.0.70 offers four options on a shell request, adding `reject-always` ("No, and don't ask again for this command"), and every request's `toolCall._meta` gains `x.ai/requestingSessionId`; the mapper already handles `reject_always`. On the probed host `touch` and `echo` ran with no `session/request_permission` on 1.0.46 and 1.0.70 alike, only `_x.ai/session_notification {pending_interaction, kind: permission}` then `interaction_resolved` about 80 ms later (a remembered grant); `rm -f` asked. agy-acp 1.4.5's `allow_always` option carries `_meta["agy.security.warning"] {severity, risk: "prompt_injection", title, message}`. Cursor's shell request now says why it asked ("Not in allowlist: echo, touch") (Pass 59).

- `agy acp`'s options are only `allow` (allow_once) / `deny` (reject_once). Its permission `toolCall` repeats the row's frame and is the only place an edit's diff appears (`content [{type: "diff", path, oldText, newText}]`; the preceding `tool_call` has none). For Antigravity (both servers), a request whose `toolCall.content` the open row has not drawn yet first emits that content as a `ToolCallUpdate` of the row at the status the row already shows (never lowered), then the `PermissionRequest` (whose `tool_call_id` names the row; an Antigravity request takes the row's title) (Pass 62).

## Questions (Antigravity)

Recorded in Pass 62 (agy 1.5.12 and agy-acp 1.4.5). Both become `QuestionRequest` / `Answer` / `QuestionResolved`, as Claude's and Codex's do; the question's row draws nothing (the card is its row). An open question is answered cancelled on interrupt and at turn end, and resolved with no answer when the process exits.

- `agy acp` asks with ACP `elicitation/create`, only when `initialize` advertised `clientCapabilities.elicitation.form` (`AcpAdapter::elicitation`, sent to `agy acp` alone). Without it the question is refused (`-32601`) and printed as chat text, and the turn ends. It follows a `tool_call {name: "ask_question", kind: "other", title: "Run ask_question", rawInput.questions [{question, options [string], is_multi_select}]}` and its `pending` update:

```json
{"jsonrpc":"2.0","id":"1","method":"elicitation/create","params":{"sessionId":"cd2c…","toolCallId":"call_8808…","mode":"form","message":"The agent has 2 questions.","requestedSchema":{"type":"object","properties":{"q1":{"type":"string","title":"Which language should the service use?","oneOf":[{"const":"1","title":"Rust"},{"const":"2","title":"Go"}]},"q1_other":{"type":"string","title":"Other","description":"Optional free-form answer to: Which language should the service use?"},"q2":{"type":"array","title":"Which features do you want?","items":{"anyOf":[{"const":"1","title":"Auth"},{"const":"2","title":"Billing"},{"const":"3","title":"Search"}]}},"q2_other":{"type":"string","title":"Other","description":"…"}}}}}
```

- Reply `{"action":"accept","content":{"q1":"1","q2":["1","3"]}}`, or free text as `{"q1_other":"Chimaera Prime"}`; both were read (the agent restated them). `decline` and `cancel` are the other actions. The adapter maps a schema of exactly that shape (`q<N>` with `oneOf` or `items.anyOf` choices, optional `q<N>_other`; ≤ 16 questions, ≤ 64 options, distinct labels): option label = `title`, multi-select for the array form, a chosen label back to its `const`, an answer that matches no option to `q<N>_other`. Nothing chosen anywhere replies `cancel`. A question with no `q<N>_other` has no field for typed text: text alone leaves the question out of the reply (or cancels the form) and follows as the next prompt, like the standalone server's question below; text beside a pick is dropped. `QuestionResolved` carries only what the agent was given. Any other form schema goes through the shared MCP-form normalizer as an `ElicitationRequest` (server "Antigravity") when it can show it, else `decline`; a non-form mode is declined.
- agy-acp 1.4.5 asks with a permission request instead: `toolCall {toolCallId: "interaction_<hex>", title: <the question>, status: "pending", rawInput: {}}` with no `kind`, options the answers (`optionId` "1", "2", …, `name` the text), every one `allow_once`, no reject. A `tool_call` with the same id precedes it, and `{status: "completed", rawOutput: "Response received"}` follows the answer. Matched exactly (Antigravity, the id prefix, no kind, ≥ 1 option, all `allow_once`) it becomes a one-question card; the reply is the selected option whose name is the chosen label. The request has no free-text field: typed text answers it `cancelled` and goes to the agent as the next prompt ("My answer to your question "…": …"), first in the queue, with no bubble of its own (the card shows it as the answer). A Stop drops it with the turn; a full queue says, in a Notice, that it could not be sent.

## MCP tool calls and pre-approval

All three honor the stdin `mcpServers` entry the daemon sends: `{type: "http", name: "chimaera", url, headers: [{name: "Authorization", value: "Bearer …"}]}`. MCP credentials go over stdin in HTTP headers, never in process arguments. Cursor sent `Authorization: Bearer …` with `clientInfo {name: "Cursor", version: "1.0.0"}` and MCP `protocolVersion: "2025-11-25"`; its docs name `.cursor/mcp.json` as the source (team dashboard servers are not loaded over ACP), and the session's list works too (Pass 45; 2026-10-14).

Every agent names the server and the tool, each in its own place; the title alone is never enough, because the model's tool name is interpolated into it verbatim (Pass 45).

- Antigravity (agy-acp 1.2.1): structured `_meta`; the title is `<server>_<tool>`; the request's `toolCall` equals the preceding `tool_call` update.

```json
{"jsonrpc":"2.0","id":0,"method":"session/request_permission","params":{"sessionId":"ee4a…","toolCall":{"toolCallId":"cab0087fdc5748f3b428d0cc480cd5a7","kind":"other","status":"pending","title":"chimaera_notify","content":[],"rawInput":{"arguments":{"text":"hello from probe"},"text":"hello from probe"},"_meta":{"mcp":{"tool":"notify","server":"chimaera"},"is_mcp_tool_call":true}},"options":[{"optionId":"allow_always","name":"Allow Always","kind":"allow_always"},{"optionId":"allow","name":"Allow","kind":"allow_once"},{"optionId":"deny","name":"Deny","kind":"reject_once"}]}}
```

- `agy acp` (1.5.12): no `_meta`. The call is `name: "mcp_<server>_<tool>"`, title `Run mcp_<server>_<tool>`, `kind: "other"`, and `rawInput` is the arguments plus an injected `toolSummary`; the request's `toolCall` repeats the frame. Options `allow` / `deny`. The MCP request itself carries `_meta {antigravity.google/artifacts_dir, conversation_id, root_conversation_id, progressToken}`. Since server and tool may both contain `_`, pre-approval reads only the consented server out of the name: `mcp_<consented server>_<tool>` with the exact title (Pass 62).

```json
{"jsonrpc":"2.0","method":"session/request_permission","params":{"sessionId":"7e03…","toolCall":{"sessionUpdate":"tool_call","toolCallId":"call_15481771948953608687","name":"mcp_chimaera_update_plan","status":"pending","kind":"other","title":"Run mcp_chimaera_update_plan","rawInput":{"items":[{"content":"one","status":"in_progress"},{"content":"two","status":"pending"}],"toolSummary":"Update probe plan"}},"options":[{"optionId":"allow","name":"Allow","kind":"allow_once"},{"optionId":"deny","name":"Deny","kind":"reject_once"}]},"id":"2"}
```

- Grok Build 1.0.46: an MCP call is its `use_tool` tool: `rawInput {variant: "UseTool", tool_name: "<server>__<tool>", tool_input}` under `_meta["x.ai/tool"].kind == "use_tool"`, the title repeating `tool_name`. The preceding `tool_call` update has `title: "use_tool"` and the unprefixed `rawInput`; a `tool_call_update` renames it; the completed update's `rawOutput` carries `{type: "MCP", tool_name, server_name}`.


## Antigravity tool rows

Recorded in Pass 62. Grok and Cursor rows keep the agent's own titles.

- `agy acp` frames carry non-spec `name` (`read_file`, `edit_file`, `write_file`, `run_command`, `ask_question`, `invoke_subagent`, `manage_task`, `mcp_<server>_<tool>`, …) and `rawInput` (`run_command {CommandLine, WaitMsBeforeAsync, toolSummary}` — `toolSummary` a one-line description such as "List workspace files"; file tools `{Path}`; `invoke_subagent {Prompt, Role, TypeName}`; `write_file` in plan mode `{ArtifactMetadata {RequestFeedback, Summary, UserFacing}, Content}` for `implementation_plan.md` under `~/.gemini/antigravity-cli/brain/<session>/`). Titles: "File notes.txt" for read and edit alike (the `kind` tells them apart), a path outside the workspace as "File ../../../…/implementation_plan.md", the command line for execute, "Run <name>" for the rest. Frames repeat everything on each update.
- agy-acp 1.4.5 titles: "Running view_file" (read), "Run edit_file?" then "Running edit_file" (edit), the command line (execute); the edit `tool_call` carries its diff and `rawInput {TargetFile, Description, Instruction, ReplacementContent, …}`; a read row `rawInput {file_path, start_line, end_line}` and `locations`. Updates rename `rawInput` fields (`command_line`) and often carry no `kind` or title.
- The adapter titles rows `Name: detail`, as the other drivers do: `Read: <file>`, `Edit: <file>`, `Write: <file>` (a `write*` tool), the file workspace-relative when under the session's folder, else its name; `invoke_subagent` is kind `agent`, `Agent: <Role>` (else the prompt's first line); an execute row keeps its command line and sets `ToolCall.command` from `rawInput.CommandLine` (clipped to `COMMAND_CAP`); another tool keeps its own name, "Run "/"Running " and a trailing "?" cut when what remains is the frame's `name` or a bare identifier. An update recomputes the title from what it carries, so "Running edit_file" does not undo `Edit: notes.txt`. Every Antigravity row's opening `rawInput` also goes out as `ToolRenderData {name, input}` when it fits 32 KiB.

## Usage and context

Recorded in the Pass 46 addendum (2026-10-15).

- ACP `usage_update` (`{used, size, cost?}`, stable since schema 1.25.0; `PromptResponse.usage` is still unstable) maps generically to `ContextUsage`. agy-acp 1.4.5 sends it (`{used, size: 1048576}` at session start and during turns), so Antigravity chats now show context; Grok and Cursor still do not (Pass 59). agy-acp 1.4.5's prompt response also carries `usage {totalTokens, inputTokens, outputTokens, thoughtTokens, cachedReadTokens, cachedWriteTokens}`, not read.
- Grok (ACP extensions, not in the spec): `_x.ai/session/info {sessionId}` → `result.result.context {used, total, usagePct, …}` (nested once more; answers before the first turn too). `_x.ai/billing {}` → `{config: {creditUsagePercent 0-100, currentPeriod: {type: "USAGE_PERIOD_TYPE_WEEKLY", start, end}, onDemandCap, onDemandUsed, prepaidBalance, …}, subscription_tier}`, answered 0.5 s after `initialize` with no session needed. After each completed Grok turn the adapter asks both: context → `ContextUsage`; billing → a deduped `RateLimit` with one window (`acp::grok_billing_usage`). A refusal is silent. The daemon's Agent-settings read runs `grok agent --no-leader stdio` → `initialize` → `_x.ai/billing`.
- `_x.ai/billing` no longer contains `config.creditUsagePercent` (live on 1.0.46 and 1.0.70 against the same account, so the change is server-side): it returns `{config: {currentPeriod {type: WEEKLY, start, end}, onDemandCap {val}, onDemandUsed, prepaidBalance, isUnifiedBillingUser, billingPeriodStart, billingPeriodEnd}, subscription_tier}`. The answer is proto3 JSON, which omits zero values, so this is an unused week: `grok_billing_usage` reads a `currentPeriod` with no percent as 0% (Pass 61).
- Antigravity: agy-acp 1.2.1's stream reported neither context nor usage (the prompt result is `{stopReason}` only); 1.4.5 adds both (above). `agy -p "/usage" --output-format json` (changelog 1.1.11: answers "without starting an agent turn, spending quota"; live `num_turns: 0`, 4 s) → `{status: "SUCCESS", command: {name: "usage", data: {groups: [{name: "Gemini Models" | "Claude and GPT models", buckets: [{id, name, window: "weekly" | "5h", remaining_fraction 0-1, reset_time ISO}]}]}}}`. An untouched bucket's `reset_time` is "now + window". Used only for the Agent-settings read ("Gemini session limit"; no reset time while `remaining_fraction` is 1).
- Cursor: nothing a host can read (no `usage_update`, no `_meta` usage, no usage subcommand; its TUI's usage panel calls Cursor's own servers). Nothing is shown.

## Native extension discovery

Separate from ACP; the daemon probes these (2026-10-01).

- `grok inspect --json` includes Claude-compatible inventory that `plugin list` / `mcp list` omit. Skill plugin identity is `source.plugin_name`; bundled skills have `source.type: "bundled"`. Grok's `/plugins` and `/mcps` open its native extensions menu. Grok local-source installation requires explicit `--trust`; Chimaera asks in the visible install terminal before setting that flag.
- `agy -p /skills --output-format json --print-timeout 15s` returns `command.name: "skills"`, `num_turns: 0`, `status: "SUCCESS"` and `command.data.skills`. Probe only known supported versions. AGY `plugin list` imports have no enablement state and omit project-only packages. A loaded skill is positive evidence for its own scope, not for another copy with the same name. In agy 1.2.14 `/plugins` is a model prompt, not a management menu; use the native plugin CLI commands.
